# 自動修正ループ ガイド

バグを自動で見つけ、直し、マージし続ける仕組みの設計と運用。実装は
`.github/workflows/auto-fix.yml` / `.github/workflows/auto-merge-deps.yml` /
`scripts/bot-budget.mjs` / `scripts/bot-change-policy.mjs`。

---

## 何を解こうとしているか

Oryzae には Issue が入ってくる経路が複数ある（人の目視、dependabot、定期セキュリティ監査）。
一方でハーネスが厳格に敷かれているため、**入ってきたバグの多くは人の判断を必要としない**。
「型を通す」「テストを通す」「アーキテクチャ規約を通す」が全部機械で担保されている以上、
残っている人間の仕事は「直す価値があるかを決めること」と「マージボタンを押すこと」だけになる。

この仕組みは、その 2 つを機械に寄せる。ただし**寄せてよい範囲を決定的に線引きしたうえで**。

同時に、費用が青天井にならないようにする。AI に探索を任せると費用は探索の深さで決まり、
事前に読めない。だから「頻度を我慢する」ではなく「**実行前に残額を計算し、足りなければ走らせない**」
という形で守る。上限は運用ルールではなくコードにする。

## 設計の骨格

### 1. 判断する主体を分ける

```
Claude          ファイルを編集する。それだけ
ワークフロー     許可領域を判定する / ガードレールを回す / コミットする / マージする
```

Claude には `gh` も `git commit` も `git push` も渡さない（`--disallowed-tools`）。
モデルが「ゲートを通したことにして進む」余地を構造的に消すため。
**マージの判断に AI の自己申告は一切使わない**。使うのは `git diff` の中身と、
ガードレールの終了コードだけである。

### 2. AI を呼ぶ前に、無料で判る仕事を全部済ませる

| 層 | 何をするか | トークン費用 |
|---|---|---|
| dependabot | 依存の更新 PR を起こす | 0 |
| `auto-merge-deps.yml` | CI が緑のグループ PR をマージする | **0** |
| CI / E2E / Security | 壊れていることを検出する | 0 |
| `auto-fix.yml` | 上で検出できないものだけを AI に渡す | 従量 |

「ライブラリのアップデート」は量が多いが判断が要らない。ここを 0 円で捌ききることで、
AI の予算を「本当に読まないと分からないバグ」に残す。

### 3. 予算は 2 段で守る

| | 効くもの | 実装 |
|---|---|---|
| 月次上限 | 「安い実行の繰り返し」で枠を溶かすこと | `scripts/bot-budget.mjs`（台帳 Issue） |
| 1 回あたり上限 | 「1 回の暴走」で枠を使い切ること | Claude CLI の `--max-budget-usd` |

片方だけでは守れない。既定は **月 ¥500 / 1 回 $0.60**。

さらに 2 つの安全装置がある:

- **予備枠** — 定期巡回は月次上限の 30% を残して止まる。「main が壊れているのに、
  巡回が枠を使い切っていて直せない」を避けるため。壊れたものを直すほうが常に優先度が高い
- **サーキットブレーカー** — 「差分は出たがマージできなかった」が 3 回続いたら、
  予算が残っていても止まる。同じ壁に当たり続けて費用だけ減るのを防ぐ

**分からないときは必ず止まる側に倒す。** 台帳が壊れていたら実行しない。
実行ログから費用が読めなかったら、その回の上限額を使ったものとして記録する。
過少計上は上限を静かに突破させるため、必ず多い側に丸める。

## 起動する経路

優先度の高い順。1 回の実行で扱うのは 1 件だけ。

| # | きっかけ | 種別 | 予備枠 |
|---|---|---|---|
| 1 | main で CI / E2E / Security が失敗した | `main-red` | 使ってよい |
| 2 | Issue に `auto-fix` ラベルが付いた | `issue` | 使ってよい |
| 3 | 週次巡回（月曜 05:25 JST） | `sweep:<slice>` | 使わない |

3 の巡回は `.github/bot/sweep-slices.json` のスライスを ISO 週番号で順に回す（1 周 8 週）。
毎回コードベース全体を読ませると費用が青天井になるため、1 回 1 スライスに絞っている。

手動実行は `gh workflow run auto-fix.yml`。Issue 番号を渡すとその Issue を対象にする。

## 何を自動マージしてよいか

判定は `scripts/bot-change-policy.mjs`（テスト付き）が行う。
**拒否リストではなく許可リスト**である。未知の領域は既定で止まる。

### 通す

- `apps/{server,client,admin}/src/**` の `.ts` / `.tsx` / `.css`
- `apps/{server,client,admin}/test/**`、`apps/{client,admin}/e2e/**`
- `packages/{shared,verify}/src/**`
- `docs/**.md`

### 止める（許可領域の内側でも優先）

| 対象 | 理由 |
|---|---|
| `apps/client/src/i18n/messages/**` | 画面に出る言葉はプロダクトの約束であり、不具合ではない |
| `**/middleware/auth*` | 認可境界。RLS を効かせるクライアント生成箇所 |
| `**/supabase-client.ts` | service role は RLS を完全にバイパスする |
| `**/*.dependency-cruiser.cjs` | アーキテクチャゲートそのもの |
| `**/instrumentation.ts`、`src/middleware.ts` | 監視の初期化と全リクエストの入口 |
| 新規追加の `apps/client/src/features/**/components/*.tsx` | 検証ハーネスが要る領域。新規部品づくりは自動修正の仕事ではない |
| 16 ファイル以上の差分 | バグ 1 件の修正としては広すぎる＝直しているつもりでリファクタしている |

許可領域の外（`supabase/**`、`.github/**`、`.claude/**`、`package.json`、`pnpm-lock.yaml`、
`scripts/check-*.mjs`、各種設定ファイル）はすべて止まる。

止まった差分は破棄され、run のアーティファクト `proposed-patch` に残り、台帳 Issue に理由が
コメントされる。「なぜ止めたか」は人が読める言葉で出す。

## ガードレールと E2E

マージ前に回すのは pre-push / CI と**同一の 7 つ**:

```
pnpm typecheck && pnpm lint && pnpm test && pnpm dep-cruise && pnpm knip && pnpm check:as && pnpm security:rls
```

3 か所（`package.json` の pre-push、`ci.yml`、`auto-fix.yml`）は常に同一に保つこと。
片方だけ緩めると「ローカルは通るのに CI で落ちる」の逆版が生まれる。

### なぜ bot の PR で CI が走らないのか

GITHUB_TOKEN が作った PR には `pull_request` のワークフローが起動しない（GitHub の再帰防止の仕様）。
マージ後の main への push も同様に CI を起動しない。したがって:

- **CI 相当はワークフロー内で回す。ここが唯一のゲートになる**
- E2E だけはここで回せない（Supabase の起動が要る）ので、マージ後に
  `gh workflow run e2e.yml` で明示的に起動する。`workflow_dispatch` は
  GITHUB_TOKEN でも起動する数少ない例外である
- その E2E が落ちれば `main-red` 経路がこのループ自身を呼び戻す（自己修復）

## 費用の見積もり

Claude Sonnet 5 は $2.00 / MTok（入力）・$10.00 / MTok（出力）、キャッシュ読みは入力の 1/10。
対象を特定済みの修正 1 回はおおむね **$0.2〜0.6**。

| | 月あたり |
|---|---|
| 上限 | ¥500（= $2.94、為替 ¥170 換算） |
| 実行できる回数の目安 | 5〜10 回 |
| dependabot の自動マージ | ¥0（AI を呼ばない） |
| Actions 消費の目安 | 60〜90 分（無料枠 2,000 分の 3〜5%） |

為替は保守側（円安側）に置いてある。1 ドルを高く見積もるほど USD 上限は小さくなり、
実際の請求は狙った円額を下回る。

台帳（Issue `[auto-fix] 予算台帳と稼働状況`）に、実行ごとの費用と結果が積まれる。
**この Issue の本文を手で編集しないこと**（JSON が壊れるとループは安全側に倒れて停止する）。

## 設定

すべて GitHub の Settings > Secrets and variables > Actions > Variables で変える。
コード変更は不要。

| 変数 | 既定 | 意味 |
|---|---|---|
| `AUTO_FIX_ENABLED` | （未設定 = 無効） | `true` のときだけ動く。**止めたい時はこの変数を消す** |
| `AUTO_FIX_BUDGET_JPY` | `500` | 月額上限（円） |
| `AUTO_FIX_JPY_PER_USD` | `170` | 為替。上げるほど USD 上限が下がる（保守的になる） |
| `AUTO_FIX_PER_RUN_USD` | `0.60` | 1 回あたりの上限（USD） |
| `AUTO_FIX_MODEL` | `claude-sonnet-5` | 使うモデル |
| `AUTO_FIX_EFFORT` | `high` | 思考の深さ（`low`〜`max`）。`aborted` が続くなら `medium` に下げる |

必要なシークレットは `ANTHROPIC_API_KEY` のみ（定期セキュリティ監査と共用）。

### 止め方

1. **今すぐ全部止める** — `AUTO_FIX_ENABLED` を消す（`auto-fix` と `auto-merge-deps` の両方が止まる）
2. **費用だけ止める** — `AUTO_FIX_BUDGET_JPY` を `0` にする（依存の自動マージは 0 円なので動き続ける）
3. **1 件だけ止める** — Issue から `auto-fix` ラベルを外す

## 運用

### 直してほしいものがあるとき

Issue に `auto-fix` ラベルを付ける。次の巡回、またはラベルを付けた瞬間に拾われる。
仕様変更・新機能・議論が必要なものにラベルを付けても、Claude が「バグではない」と判断して
何もせずに終わる（それも 1 回ぶんの費用がかかるので、バグに対してだけ付けること）。

### 空回りしていないか確かめる

台帳 Issue の「実行履歴」の `結果` 列を見る。

| 結果 | 意味 | 対応 |
|---|---|---|
| `merged:#N` | 直してマージした | — |
| `no-fix` | 探したが直す価値のあるものが無かった | 正常。巡回では普通に起きる |
| `blocked` | 差分は出たが許可領域外だった | 続くならスライスか指示を見直す |
| `gates-failed` | 差分は出たがガードレールに落ちた | 続くなら指示か対象が悪い |
| `aborted` | 1 回あたりの上限に当たって打ち切られた | 続くなら `AUTO_FIX_PER_RUN_USD` を上げる |

`blocked` / `gates-failed` が 3 回続くとサーキットブレーカーが働いて停止する。
原因を直してから、台帳 Issue に成果のある実行が 1 件積まれれば自動で解除される
（すぐ解除したい場合は台帳 Issue を閉じる。次回に新しい台帳が作られる＝当月の使用額もリセットされる点に注意）。

### 依存更新で自動マージされないもの

`auto-merge-deps.yml` が通すのは、`.github/dependabot.yml` が更新の種類まで保証している
**グループ PR だけ**である:

- `minor-and-patch` グループ（設定で minor / patch に限定されている）
- `actions` グループ（CI 自身がその新しい action で走った結果が緑である）

単独の PR（major 昇格、security update）は自動マージしない。人が見る。
更新の種類を PR タイトルから推測しにいくと、いつか静かに major を通してしまうため。

## 意図的に採らなかった選択肢

- **全 PR に AI レビューを掛ける** — PR 数に費用が比例する。月 40〜60 本の PR がある以上、
  上限が読めなくなる。`security.yml` が同じ理由で定期監査に寄せているのと同じ判断
- **費用の台帳をブランチや Actions キャッシュに置く** — 人の目に触れない。キャッシュは 7 日で消え、
  Actions variables は GITHUB_TOKEN から書けない。Issue なら「今月いくら使ったか」が
  リポジトリを開けば読める
- **PAT を用意して bot の PR で本物の CI を走らせる** — 手動のシークレット管理が増えるうえ、
  同じゲートを 2 回課金することになる。ワークフロー内で回す形にした
- **もっと安いモデルを使う** — Haiku との差は約 2 倍だが、ガードレールに落ちた実行は
  費用が丸ごと無駄になる。1 回で通る確率のほうが効く
