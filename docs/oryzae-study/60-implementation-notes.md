# 60 — 実装時の決着（仕様と実コードのズレ）

`00-overview.md` 〜 `50-rollout.md` は実装前に書かれている。リポジトリを読んだ結果、
いくつか前提が実際と違っていた。**このファイルが後から書かれた分だけ新しい**ので、
矛盾したらここを優先する。

## 1. `readiness` は上流に既にあった

`10-data-contract.md` は「上流にあるのは `FermentationSummary.status` だけ」としているが、
これは誤り。次のものが既にある。

| もの | 場所 |
| --- | --- |
| `readinessScore` (0..1) を返すドメインサービス | `fermentation-eligibility.service.ts` の `evaluateEligibility()` |
| それを組む usecase | `get-fermentation-readiness.usecase.ts`（admin から使用済み） |
| 永続化カラム | `user_fermentation_state.readiness_score numeric(3,2)` |
| 本人の SELECT を許す RLS | `supabase/migrations/00014_...sql` |

00014 のコメントに「readiness は admin ダッシュボード表示と **Jar アニメーションへの反映**を
意図する」と明記されており、最初からユーザーに出す前提で作られていた。

**決着: 案 A。** ただし新規実装ではなく、既存 usecase を本人向けに公開するだけ
（`GET /api/v1/fermentations/readiness`）。マイグレーション不要。

**案 B は採らない。** 案 B の式は `pickledSinceLastFermentation / threshold` だが、実際の
発火条件は `countCharsByUserIdSince()` ＝ *fermentation_enabled に関わらず全エントリの
合計文字数*。案 B は「サーバーの条件が変わると嘘になる」以前に、書かれた時点で既に嘘。

### 返す形

admin 版は `threshold` / `charsCurrent` / `hoursElapsed` まで返すが、本人向けは
`{ readiness, eligible, nextRunAt }` に絞る。「readiness を数値で出さない」方針
（`00-overview.md`「コピー」）と、閾値を晒さないため。

### `status` はサーバーから来ない

`StudyState.fermentation.status: 'idle' | 'fermenting' | 'completed'` は瓶の見た目の語彙で、
上流に 1:1 の対応が無い。サーバーの `FermentationStatus` は
`'pending' | 'processing' | 'completed' | 'failed'` で、しかも**発酵 1 件ごとの状態**
（ユーザーの状態ではない）。

**決着: クライアントで合成する**（`use-study-state.ts`）。

- `completed` … 未読の完了発酵がある。未読判定は localStorage にしか無く、**構造的に
  サーバーでは決められない**
- `idle` … 完了発酵が無く readiness が 0
- それ以外 … `fermenting`

## 2. `notebooks` は新設した

`GET /api/v1/entries/monthly-counts`。`created_at` は timestamptz、「月」はユーザーの
ローカル暦月なので、board API と同じ規約で `tzOffsetMinutes` を受ける
（これが無いと JST の月初 0–9 時の記録が前月に落ちる）。

実装は Postgres 集計ではなく「`created_at` だけを読んでサーバーで畳む」方式。
`user-me.ts` の `selectAllRows` と同じ id カーソルページングを使う（offset だと読んでいる
最中の INSERT でずれる）。行数が問題になったら RPC に差し替える — API 契約は変わらない。

**クライアント近似は不可。** 既存の `/entries?limit=20` から数えると 40 件の月が 20 件に
見え、手帳の厚みが嘘になる。

## 3. 「漂う言葉」は発酵中には存在しない

`fermentation_keywords` は `run-fermentation.usecase.ts` で `withStatus('completed')` の
直前に一括保存される。発酵は段階的な処理ではなく **LLM の 1 バッチ**なので、
`status: 'fermenting'` の間にキーワードは 1 件も無い。

`00-overview.md` の「readiness に応じて言葉が漂う／readiness が低ければ表示語数も減る」は
上流の作りと成立しない。

**決着: 直近に完了した発酵のキーワードを漂わせる**（＝いま漬けているものではなく、
前回の残り香）。追加 API は要らず、表示語数を readiness で絞れば「発酵が浅いほど語が少ない」
という見た目の規則もそのまま満たせる。

## 4. ファイル配置は `20-3d-component.md` と変えた

doc の配置は client の dep-cruise ルール 3 つに当たる。

- `shared-no-device-detection` … `features/shared/**` → `components/device-view` を禁止
- `reach-shared-purity` … `features/shared/**` → `features/{pc,sp}/**` を禁止
- `protected-pages-use-device-view` … `app/(protected)/**/page.tsx` に device-view を要求

また `scene/` を `features/pc/study/` に置くと `reach-slice-isolation` により
`features/sp/study` から import できず、SP 用に丸ごと二重実装になる。

**決着:**

```
apps/client/src/features/shared/study/
  types.ts                        StudyState など
  layout.ts                       PC/SP の座標・fov・尺度（端末名ではなく「配置」として持つ）
  constants.ts                    duration / easing / カメラ距離の唯一の置き場
  scene/                          three.js だけに依存する純関数（React 非依存）
    materials.ts jar.ts books.ts board.ts camera.ts labels.ts scene.ts
  hooks/use-study-state.ts
  components/study-canvas.tsx     layout を受け取る。端末を判定しない
  components/study-chrome.tsx
  components/entry-list-overlay.tsx
  components/study-fallback.tsx
apps/client/src/features/pc/study/components/pc-study.tsx   PC_LAYOUT を渡す薄い入口
apps/client/src/features/sp/study/components/sp-study.tsx    SP_LAYOUT を渡す薄い入口
apps/client/src/app/(protected)/study/page.tsx               ここで DeviceView 分岐
```

`study-canvas` には `device` 文字列ではなく `layout` オブジェクトを渡す。shared の中で
端末を分岐しないという規約に正直に沿うため。

## 5. SP のボードは**存在しない**

`app/(protected)/board/page.tsx` は `<DeviceView pc={<BoardView />} />` で `sp` を
渡していない。つまり SP でボードを開くと「スマホ未対応」が出る。

`30-branch-and-commits.md` のコミット 10「SP のボードから右ペインを外し、カードを
ドラッグできるように」は、実際には **SP ボードの新規実装**であって、規模が他の全コミットに
匹敵する。かつ「既存の board 画面は変更しない」という今回の縛りとも衝突する。

**決着: 当初は別 PR に分離したが、この PR で実装した。**
`features/sp/board/` に新設し、`/board` の `DeviceView` に `sp` を渡した。

- `sp-board-surface.tsx` — 見た目と指の操作（検証可能な純粋な描画）
- `sp-board.tsx` — 取得と初期フィット

PC の `BoardView` は触っていない。`reach-slice-isolation` により `features/sp` から
`features/pc` は import できないので、カードの描画は SP 用に別に書いた。とはいえ
コピーではない — PC が持つ意味的ズーム・選択・回転・リサイズ・ツールバー・ミニマップは
どれも無く、指の移動 1 つに絞ってある（`no-cross-device-duplication` の閾値 0.6 に対して
十分低い）。

**仕様との差: 位置を保存する。** `30-branch-and-commits.md` のコミット 10 は
「位置の永続化はしない（この段では見た目だけ）」としているが、`40-acceptance.md` は
「離した位置に留まる」と書いており、保存しないとリロードで配置が消える。PC が使っている
`useBoardSave`（debounce つき PUT）がそのまま使えるので、指を離した時に投げる。

**日の切り替えは付けていない。** 00-overview.md が SP について挙げているのは
「日付とカード枚数だけを隅に小さく浮かせる」だけで、日付ナビゲーションに触れていない。
そのため当日のボード固定になっている。過去の日を見る導線が要るかは別途の判断。

## 9. 残っている穴: 古い月の一覧が空になる

一覧オーバーレイは `useEntries`（`GET /api/v1/entries?limit=20`）が取ってきた
**直近 20 件**を月で絞っているだけ。そのため、20 件より古い月を選ぶと
「この月の記録はありません」と出る。

実機で確認した食い違い（2026-09-04 時点のテストアカウント）:

| 月 | 手帳／棚が言う件数 | 一覧が出す件数 |
| --- | --- | --- |
| 2026.09 | 6 | 6 |
| 2026.08 | 14 | 14 |
| 2026.04 | 1 以上（棚に背表紙がある） | **0** |

見出しも `2026.04 — 0 ENTRIES` と出るので、**手帳の厚みと矛盾した数字を自分で
名乗ってしまう**のが厄介。件数は `monthly-counts`（全期間の集計）から来るのに、
一覧は直近 20 件しか見ていない。

直し方は 1 つで、`GET /api/v1/entries` に月の絞り込みを足すこと
（`questionId` と同じ形の `month=YYYY-MM`。サーバー側は `localDayRange` と同じ
`tzOffsetMinutes` を受けて期間で絞る）。クライアントでページングを繰り返して
埋めるのは、月が古いほど往復が増えるので採らない。

**→ §26 で直した。**

## 10. 端末の切替は `?device=pc|sp|auto`（URL で行う）

端末は middleware が `device-pref` cookie（無ければ UA）から確定し `x-device` ヘッダで
渡す。切り替えるには cookie の書き換えとリロードの両方が要るため、PC と SP を見比べる
たびに DevTools の Console を開くことになっていた。

最初は画面右下にレビュー用の切替スイッチ（`DeviceSwitch`）を置いていたが、**消し忘れると
本番のログイン後の全画面に出る**うえ、それを止めるのが人の記憶しか無かった。このリポジトリは
`check:as` / `knip` / `dep-cruise` / `security:rls` / `verify-coverage-gate` と、守りたいことを
全部機械に持たせてきた場所なので、ここだけ人力なのは浮いている。

そこで**恒久の仕組みに寄せた**。middleware は既に `?lang=` を cookie に固定しているので、
同じ形で `?device=` を受ける。`?study=on` とも操作感が揃う。

```
?device=sp     … SP として描く（cookie に憶える）
?device=pc     … PC として描く
?device=auto   … 切替を捨てて UA 判定へ戻す
```

**そのリクエストから効かせる**のが要点。cookie はレスポンスにしか乗らないので、保存だけ
だとリロードするまで反映されず「付けても何も起きない」ように見える。middleware は
`?device=` を読んだ値をその場の解決に使い、同時に cookie にも書く。

`auto` を用意するのは、**入る道だけあって出る道が無い切替を作らない**ため（`?study=auto`
と同じ理由）。一度 sp に固定した端末が UA 判定へ戻れないと、以後ずっと嘘の見え方をする。

契約は `test/middleware.test.ts` が固定している。

## 11. 瓶の言葉は「問いごとの最新キーワード」を全部浮かべる（原案からの拡張）

原案は「直近に完了した発酵のキーワードを最大 6 語」だった。ここを広げて、
**設定している問いごとの最新のキーワードを全部**浮かべる。受信箱
（use-fermentation-inbox）が問いごとに最新 1 通へ畳んでいるので、その全部の詳細から
集める（問いは生存が最大 3 件なので往復も 3 回に収まる）。

語ごとの大きさは 0.72〜1.38 倍でばらす。**`Math.random()` では決めない** —
状態が更新されるたびにシーンを組み直すので、乱数だと大きさが毎回変わって画面が
ちらつく。語の文字列から決めるので、同じ語は常に同じ大きさになる。

大きさがばらつくぶん、行間は一律ではなく**隣り合う 2 語の高さ**から決める
（一律だと大きい語どうしが触れる）。全部が入らないときは行間を詰めて収め、
詰めても入らない語だけを落とす。

## 12. 完了した瓶の泡は「止める」から「ゆっくり上げる」へ変えた

仕様（`00-overview.md`「完了すると泡が止み」/ `21-3d-parameters.md`「完了時 0＝静止」）と
原案（`speedScale = done ? 0 : ...`）は、発酵が完了したら泡を**止める**と決めている。
そこだけ外している。

理由: 手紙が届いている瓶はいちばん長く見る状態で、そこで泡が完全に止まると
「壊れている」と読まれる（実機のレビューで 2 度指摘された。ロード中だけ泡が上がり、
データが届くと止まるので、なおさら不具合に見える）。

**静けさは失っていない。** 泡の数は 30 → 4 に落ちたままで、封も浮かぶ。速さだけ
readiness 0.12 相当のごく遅い流れにしてある。戻すなら `COMPLETED_DRIFT` を 0 にする。

## 13. 瓶の言葉は液面で頭打ちにしない

原案は言葉を「液面までの高さ」に収める。ここも外している。

readiness が低いと液面までの高さが 0.1 ほどしか無く、そこに収めようとすると
**2 語目以降が全部落ちて 1 語しか浮かばない**（実機でそうなっていた）。問いごとの
キーワードを全部見せる（§11）という指定と両立しないので、入り切らないぶんは瓶の
空いている高さへ伸ばす。上限は首がくびれ始める手前（2.35）で、コルクには重ならない。

液面に余裕があるときは従来どおり液面までに収まるので、発酵が進んだ瓶の見え方は変わらない。

## 14. 呼吸の周期は「1 秒」ではない（21-3d-parameters.md の注記が誤り）

`21-3d-parameters.md` は呼吸を「y に `sin(t) * 0.05`（1s）」と書いているが、
**式と注記が食い違っている**。原案の `t` は `Date.now() * 0.001` ＝ **秒**なので、
`sin(t)` は角速度 1 rad/s、つまり周期は **2π ≒ 6.3 秒**。1 秒ではない。

注記のほうを信じて 1 秒周期で実装したところ、カメラが毎秒上下して画面全体が
小刻みに揺れ、「マウスを動かしていないのに行きつ戻りつして気持ちが悪い」という
報告になった。振幅（0.05）は小さくても、周期が 6 倍速いと酔う。

同じ取り違えが言葉の揺れと周回にもあった。原案の係数はどれも **rad/s** で、
2π を掛けてはいけない。

| もの | 原案 | 周期 |
| --- | --- | --- |
| カメラの呼吸 | `sin(t)` | 約 6.3 秒 |
| 言葉の上下 | `sin(t * 0.3)` | 約 21 秒 |
| 言葉の周回 | `cos(t * 0.1)` | 約 63 秒 |
| 輪郭の呼吸 | `sin(t * π/2)` | 4 秒 |
| 封の浮遊 | `sin(t * 0.8)` | 約 7.9 秒 |
| 泡の横揺れ | `sin(t)` | 約 6.3 秒 |

輪郭・封・泡は最初から合っていた。ずれていたのはカメラと言葉の 3 つ。
`camera.test.ts` に「1 フレームあたりの変化が振幅の 2% を超えない」という
テストを置いてあるので、速くしすぎると落ちる。

## 15. 前回の書斎を憶えて、開いた瞬間に出す

書斎を開くたびに瓶の言葉とボードのカードを取り直していて、その間ずっと机と壁が空に
見えていた（発酵の詳細は問いの数だけ往復するので、いちばん遅い）。

`lib/stale-cache.ts` に stale-while-revalidate の器を置き、`use-study-state` が
取り終えた `StudyState` を localStorage に憶える。次に開いたときは**取得を待たずに
前回の絵を出し**、裏で取り直した本物が届いたら差し替える。取得そのものは止めていないので、
古い値が長く残ることはない。

決めごと:

- **鍵は利用者ごとに分ける**（`study:<userId>`）。端末を共有していると、前の人の
  記録の冒頭や発酵の言葉がそのまま出てしまう
- **ログアウトで全部捨てる**（`clearAllStaleCaches`）。ここには日記から作った内容が入る。
  接頭辞で自分の分だけ消すので、下書きや既読は巻き添えにしない
- **読むときに形を確かめる**。中身は前のバージョンの自分が書いたもので、信用して
  そのまま 3D へ流すと形が変わった瞬間に落ちる。版（`CACHE_VERSION`）と型ガードの二重で止める
- **日付だけは憶えた値を使わない**。日をまたぐと当月の手帳が前月として出る
- 認証 context はこの hook から読まない。読むと `AuthProvider` の中でしか動かなくなり
  単体で試せなくなるので、利用者は呼び出し側から渡す

## 16. サイドバーはサブ画面でも消す

当初は書斎ホームでだけ左サイドバーを外していたが、jar / board / entry でも外す。
書斎が「唯一のグローバルナビゲーション」（00-overview.md）である以上、行き先の画面にだけ
旧ナビが残るのは半端で、戻り道が左上のマークと左のサイドバーで二重になる。

これに合わせて `entry-editor` の左端を `SIDEBAR_WIDTH`（定数 80px）から
`var(--sidebar-width, 0px)` に変えた。定数のままだと、サイドバーを描かない画面で
左に 80px の隙間が残る。ボードのツールバーは元から同じ変数を読んでいる。

**SP のボトムナビも同じ条件で外す。** 当初は「消すと `/questions` へ行けなくなる」ため
残していたが、問いの入口を瓶の中へ移した（§17）ことで理由が消えた。判定は
`{!studyHome && <SpBottomNav />}`（サイドバーと同一条件）なので、**フラグ off の間は
従来どおり全画面に出る**。

## 17. SP の瓶は「壜のまわりを問いが回る」形にした（原案の範囲外）

`docs/oryzae-study/` は書斎ホームの仕様で、SP の `/jar` そのものは対象外だった。
ボトムナビを外すと問いへ行けなくなるため、PC の瓶と同じ「中央に壜、そのまわりに問いの円」
という構図を SP にも持たせ、問いの管理をそこから開くようにした。

**PC と違うところ（＝盤面を持たない）。** PC は問いの円を好きな場所へドラッグして置ける
「世界」だが、SP は片手で持つ縦長の画面で、置き場を作っても指で選び分けられない。
代わりに軌道の上へ等間隔に並べ、**横に払って回して選ぶ**。重ならないことが構造で
保証されるので、問いが増えても破綻しない。

決めごと:

- **回転は縦軸まわり**（横楕円に射影）。横軸まわりに回すと円が上下に散り、縦長の画面で
  壜と重なって読めなくなる。手前は壜の裾、奥は壜の首、と縦にずらして奥行きを出す
  （`features/sp/fermentation/orbit.ts`）
- **指を離しても止めない。** 0 まで減速すると「触るまで動かない置物」に見える。
  既定の速さ（`IDLE_SPIN`）へ戻す。`prefers-reduced-motion` のときだけ止める
- **回転は React の state ではなく DOM の style に直接書く**。60fps で state を回すと
  円の中の SVG まで毎フレーム差分計算に乗る。React に渡すのは「正面がどれか」だけ
- **回した直後の指離しで円を開かない。** `click` は `pointerup` の**後**に来るので、
  pointerup で「ドラッグ中」を降ろすと、回し終えた位置の円が開いてしまう。回したかどうかを
  次の click まで持ち越す（`SpJarOrbit/drag-does-not-open` がこれを固定している）
- **円の重なり順は軌道の中で閉じる**（`isolation: isolate`）。円は奥行きを z-index 0..1000 で
  表すので、層を閉じないと開いた円（z-20）やシート（z-30）を突き抜ける
- **問いテキストは畳んで、縮めない。** PC は円周に収まるまで字を小さくするが、SP で
  それをやると読めなくなる。読める大きさ（12–17px）を先に決めて、入らない分を「…」で
  畳む（`ring-text.ts`）。`textPath` は入らない分を黙って捨てるので、畳まないと末尾が消える
- **円の中では中身を読ませない。** 言葉・抜粋・手紙は「在ること」だけを示す押せる的で、
  本文はボトムシート（`SpElementSheet`）で読む。小さな円に本文を詰めると全部読めなくなる

## 18. 壜の絵を shared へ切り出した（PC の瓶にも影響がある）

SP の瓶にも「PC と同じ壜」を中央に置くため、`JarView` の中にあった壜の絵を
`features/shared/fermentation/components/jar-bottle.tsx` へ移した。**PC 側の DOM は
そのまま移設した**ので見た目は変わらない…はずだったが、2 点だけ実際に変わっている。

1. **中の言葉の切り抜きを比率指定に直した。** CSS の `clip-path: path(...)` は座標を
   絶対 px で解釈する。壜の絵は viewBox 480x600 を器に合わせて伸縮するので、器が
   480x600 から離れるほど絵と切り抜きがずれる。PC（500x620）ではほぼ一致していて
   気づかなかったが、SP（幅 240 前後）では切り抜きが壜の 2 倍になり、中の言葉が
   **壜の外へこぼれた**。`clipPathUnits="objectBoundingBox"` の SVG clipPath に変えて、
   器の大きさに依らず一致するようにした（`jar-path.ts` の `toUnitPath`）。
   PC でも数 px ぶん切り抜きが正確になる
2. **絵の器を viewBox と同じ比（480:600）に固定した。** 比が違うと SVG は余白を作って
   中央に寄る（preserveAspectRatio）ため、1 の切り抜きとずれる。PC の器は 500x620 で
   比が 0.806 だったので、描画は 496x620 になる（従来の "meet" 縮尺と同じ結果）。
   中の言葉は器の幅に対する比（`cqw`）で書くようにしたので、PC では従来比 1.03 倍に
   なる（480 → 496）。目視で分かる差ではない

## 19. 手帳が開く段取りの取りこぼし 3 件

実機で「1 ページしかめくれない / 右側にいつまでも表紙が出ている / 見開きが出てこない」と

2. **見開きの罫を紙（leaf）に引いていた。** 原案は**束の上面**（右の頁）と**表紙の裏**

## 23. 出ていくときは切り替えず溶暗する

書斎から jar / board / entry へ移るとき、書斎が一度に消えて行き先が出ていた。
**遷移の後半に重ねて書斎を薄くする**（`leaveFadeStart` / `leaveFadeDuration`）。
カメラが着くのと同時に消え終わるので、待ち時間は増えない。行き先は同じ地の色の上に
現れるため、切り替わりではなく溶暗に見える。

- 長い遷移（手帳 2330ms）は `DURATION.canvasFade`（600ms）ぶん
- 短い遷移（ボード 900ms）は遷移の半分（450ms）まで。最初から薄くするとカメラが
  動いているのが見えなくなる
- 書斎へ戻ってきたときは逆に 0 → 1（`DURATION.screenFade`）。サブ画面から戻ったときに
  書斎が唐突に現れない

`crossfadeOpacity` は定義だけあって誰も呼んでいなかった（テストだけが参照していた）。
実際に使う形に置き換えてある。

## 25. 取りに行って届かなかったときは、前回の書斎を出す

レート制限（429）に当たった直後、机の手帳も壜の言葉もボードのカードも消えて**空の部屋**が

- 取りに行く hook（readiness / 受信箱 / 月別件数 / 記録）に `error` を足し、

- どれか 1 つでも落ちていたら、前回の書斎をそのまま出す（通信の失敗はまとめて起きる）
- **届かなかったときは憶えている中身を上書きしない。** 空で塗り潰すと、次に開いたときも
  空になる

本当に空（200 で空配列）なら空で出す。憶えた中身を出し続けると、全部消した人に
消えたはずの物が見え続ける。

### 残っている穴: 書斎は 1 回開くたびに 8 往復する

`general` の上限は **60 リクエスト/分・利用者**（`rate-limit.ts`）。書斎を 1 回開くと
users/me・questions・fermentations（**2 回**）・fermentations/readiness・
entries/monthly-counts・entries・board の 8 往復が走る。行き来を繰り返すと数分で上限に届く。

`/api/v1/fermentations` が 2 回なのは、`(protected)/layout.tsx` の `useUnreadLetters` と
書斎の `useFermentationInbox` が同じものを別々に取っているため。書斎は `questionText` を
使っていないので、受信箱を未読側と 1 本化すれば `/questions` ともども 2 往復減らせる。
ただし `UnreadState` は `lib/` にあり、発酵ドメインの型を持たせられない（lib はドメインを
知らない）。**共有の取得を `features/shared/fermentation` 側の provider へ移す**のが筋。

## 26. 一覧の月絞りをサーバーへ渡した（§9 の解消）

§9 に書いた穴（棚から古い月を開くと必ず「この月の記録はありません」）を直した。
`GET /api/v1/entries` に `month=YYYY-MM` を足し、絞り込みをサーバーに任せる。

- 区間は `localMonthRange`（新規）が決める。件数（`countByMonth` → `localMonthKey`）と
  **同じ月の切り方**であることをテストで固定した。ずれると、手帳の厚みが言う件数と
  一覧の件数が食い違う（月初 00:00〜09:00 の記録が片方だけ前月に入る）
- `tzOffset` は月別件数と同じものを送る。送らないと上のズレを踏む
- 月は `01`〜`12` だけ受ける。`2026-13` を通すと空の区間で必ず 0 件になり、
  「その月には無い」と区別がつかない
- クライアントは `useEntriesByMonth`（新規）。1 往復 100 件で、ちょうど届いたときだけ
  次を見に行く（ふつうの月は 1 往復で終わる）。上限 10 ページ
- 取りに行っている間は「この月の記録はありません」を出さない（`list_loading`）。
  手帳の厚みが件数を言っているぶん、0 件の断定はとくに嘘っぽく見える

`useEntries`（直近 20 件）はそのまま。書斎ではホバーに出す日付の範囲づくりと、
月を選んでいないときの一覧に使う。

### §26 の続き: 手元でもう一度絞っていた

サーバー側を直したのに一覧はまだ空だった。**クライアント側の配線が入っていなかった**
（前の作業でパッチを流し忘れた）ことに加え、通していても効かない罠がもう 1 つあった。

`EntryListOverlay` が `createdAt.slice(0, 7)` で**もう一度**月を絞っていた。これは
**UTC の月**での判定なので、サーバーが利用者のローカル暦月で正しく返した記録のうち、
月初 00:00〜09:00（JST）に書いたものを前月扱いで落としてしまう。二重に絞る意味も無い。

- 絞り込みは呼び出し側（サーバー）に一本化し、オーバーレイは**渡された行をそのまま出す**
- 同じ理由で行頭の日付（`formatRowDate`）も**ローカル暦日**にした。文字列を切ると
  6 月の一覧に `05.31` の行が混じる

## 30. SP のボードで作る・直す

見えているのに触っても何も起きない状態だった（動かせるだけ）。PC（#524）と同じ
「**選んでいるものに応じて中身が入れ替わる道具箱**」を SP 用に作り直して置いた。

- 何も選んでいない … 抜粋 / 写真（作るもの）
- カードを選んでいる … 編集 / 前面へ / 外す（そのカードにできること）

常に全部を並べないのは、縦画面に横幅が無いから**だけ**ではない。「いま何ができるか」を
道具の側が示すほうが、押せるものを探させるより速い。

PC のツールバーを import せず作り直したのは reach 分離（pc ⇔ sp 禁止）と、指と矢印で
当たりの大きさも並べ方も違うため。**共有するのは語彙（i18n キー）と考え方だけ**にした。

### 触れたのか、動かしたのか

指は必ず数 px 揺れる。`pointerup` を無条件に「保存」にすると、触れただけで 1px ずれた位置が
毎回保存され、逆に「選ぶ」手段が無くなる。掴んでからの移動量を測り、`TAP_SLOP`(6px) 未満なら
**選ぶ**、超えていれば**保存する**。

`pointercancel`（別のものに指を横取りされた）は「選ぶ」に倒さない。利用者が離したわけでは
ないので、押した覚えのないカードの操作が道具箱に出てしまう。動かしたぶんだけ保存して掴みを解く。

### つまみは 1 つ（角）

回転と拡大を別々のつまみにすると、どちらも指より小さくなって掴み分けられない。角の 1 点で
**中心からの向き＝回転・中心からの距離＝倍率**を同時に扱う（`resizeFromHandle`）。

- 縦横比は変えない。写真が引き伸ばされる操作を作らない
- `MIN_CARD_SIZE`(60px) より小さくしない。掴めなくなったカードは戻せない
- つまみは盤面の倍率で**逆スケール**する（#533 と同じ）。縮小して眺めている時ほど、
  つまみは指の大きさで無いと当たらない
- 回転は `normalizeDegrees` で -180..180 に畳む。何周もすると保存する数字が読めなくなる

### 写真

送信前の縮小は PC のダイアログと同じ処理なので、`lib/image.ts` に出して両方から呼ぶ
（`resizeImage` / `readImageDimensions`）。SP には貼り付けもドロップも無いので、
入口は `<input type="file" accept="image/*">` の 1 つだけ。

## 31. 問いは切らない — 足りなければ輪を増やす

円の外周に置ける字数は、読める大きさ（12px 以上）だと直径 176px で 24 字ほど。一方
問いは最長 64 字（`MAX_QUESTION_STRING_LENGTH`）ある。**入らない分を「…」で畳んでいたが、
読めない問いを円に置く意味は無い**ので、字を小さくするのではなく**輪を増やす**ことにした。

- 増やす向きは**外側**。円の内側は中身の予告（言葉・抜粋）の席で、そこへ字を伸ばすと
  予告を押しのける
- 読む順は外の輪から内へ。12 時の位置では外の輪が上に来るので、横書きの行と同じ順になる
- 決め方は「まず輪の数、次に字の大きさ」。1 重で入るなら字を落としてでも 1 重にする
  （逆順にすると、少し長いだけの問いでも二重になって円が賑やかになる）
- 輪の間隔は行送り（字の 1.15 倍）を下回らない。縁からの距離だけで決めると、
  字が大きいときに 2 本がくっついて 1 本の帯に見える

### 「置ける字数の合計」で判定してはいけない

欧文は語の途中で割らないので、1 行は容量より短くなる。合計字数だけを見て「入る」と
判断すると、流し込んだ結果あふれた末尾が**黙って落ちる**（`textPath` は収まらない分を
捨てる）。実際に流し込めたかで判定する。`ring-text.test.ts` は 1〜64 字すべての長さで
1 字も落ちないことを見ている。

拡大した円（`SpQuestionZoom`）も同じ計算を使う。輪が外へ増えるぶん、円は
`min(88vw, 56vh)` から `min(80vw, 52vh)` に控えめにした（そのままだと 2 重目が画面の縁で切れる）。

## 32. `textPath` は「経路の外の字」を描かない — 起点は 6 時

実機で「自然環境を身に宿すためのデザインとは？」の**頭 3 字が消えていた**。字数の計算
（§31）は通っていたのに、描画で落ちていた。

原因は経路の起点と `startOffset` の組み合わせ。`textAnchor="middle"` の字は起点の前後へ
伸びるが、**経路の頭より手前へ出た字は描かれない**。頭が 9 時・`startOffset="25%"`（12 時）
だと、12 時から遡って使えるのは四半周だけ ＝ **円周の半分しか置けない**。

    直径 172px / 円周 478px / 17px 字 → 19 字 = 349px
    25% 地点 = 119px、その手前へ 174px 伸びる → 55px（3 字）が経路の外

起点を 6 時に移し `startOffset="50%"` にすると、12 時を中心に前後半周ずつ使える。
継ぎ目（頭と終わりが出会う点）が 6 時に来るのも都合がよい — 問いは 12 時を中心に置くので、
隙間はいちばん読まない側へ寄る。`ringPath` と `RING_START_OFFSET` は必ず対で使う。

### 落ちた字は `getComputedTextLength` では見つからない

あれは**描かれたかに関係なく**送り幅の合計を返すので、経路から落ちた字も長さに数える
（実際、これで書いた invariant は壊れた実装でも通ってしまった）。`getExtentOfChar(i)` を
1 字ずつ見て、幅も高さも 0 なら描かれていない。`lib/verify/text-path-invariant.ts` の
`textPathFitsInvariant()` がこれを全 fixture で見る（版組みの無い jsdom では黙って通るので、
ブラウザの /verify dashboard で効く）。壊れた実装に戻すと
「8/35 字が描かれていない」と落ちることを確認済み。

## 33. 実機レビュー: 部屋の名前・左上のマーク・読み込み中の 3 択

書斎を実機で見てもらった指摘のうち、判断を伴わない 3 つ。

### 部屋の名前は 1 つだけ

下端に `t('title')`（書斎）と `STUDY` を縦に並べていた。同じものの日本語と英語が
上下に並ぶと、**別々の 2 つの何か**に見える。本文が日本語なので日本語だけ残した。

検証は文言そのもの（以前は `'STUDY'` を `textContent` で探していた）ではなく
`data-study-caption` の有無で見る。語を変えるたびに検証まで壊れるのは、契約の置き方が
間違っている。

### 左上のマークは、書斎でも戻るときでも同じ絵

書斎の左上はブランドの `o` 一文字だった。「左上の 0（または O）がずっと出ていて意味が
分からない」と報告された。サブ画面の「書斎へ戻る」は既に書斎の縮図（机・壜・手帳・板）に
してあったので、**同じ絵を共有する**（`study-mark.tsx`）。

同じ絵にするのは揃えるためだけではない。**戻り先が「さっきまで居たあの部屋」だと
一目で繋がる**ようにするため。片方だけ絵にしても、行き先と戻り先が同じ場所だと分からない。

`StudyMark` は検証ユニットにしていない。状態も分岐も持たない装飾で、2 か所で同じ絵に
なることは 1 ファイルを import している事実が保証する。ユニットにすると親の subtree に
契約が二重に出るだけになる（実際そうなった）。両親の invariant が `data-study-mark` で見る。

### 読み込み中に「3 つの選択肢」を出さない

書斎へ入るたびに謎の 3 択が一瞬現れて消える、と報告された。正体は `StudyFallback` で、
WebGL 非対応と three.js の読み込み中の**両方**に同じ画面を使っていた。

3 つのリンク（瓶・記録・ボード）は「書斎が**出せない**から代わりにここへ行ってくれ」と
いう意味を持つ。すぐ書斎に置き換わる読み込み中に出すと、意味の違う画面が割り込んだ
ように見える。読み込み中は書斎の絵だけを置いて、これから出るものの形を予告する。

## 34. 手帳を開くのに 2.3 秒かかっていた

「最初にエントリーを開くときのアニメーションを、1 秒以内の体感にしたい」という指摘。

段取りは 真上へ寄る(950) → 表紙が開く(760) → 見開きへ寄る(620) の**直列**で、
合計 2330ms。カメラが着くまで画面は切り替わらないので、そのまま待ち時間になっていた。

段を削ると振り付け（寄る → 開く → 覗き込む）が壊れる。**順序を保ったまま重ねた**:

```
真上へ寄る 560ms ────────────
表紙が開く      308ms ──────────── 460ms
見開きへ寄る            607ms ──────────── 360ms   → 合計 967ms
```

人は「表紙が開き始める」のを、カメラが止まり切る前から読み取れる。止まるのを待つ必要が
あるのは機械の都合でしかない。重なりは `JOURNAL_OVERLAP`（前の段が何割進んだら次を
始めるか）で持つ。

**上限はテストで見張る。** `OPEN_BUDGET_MS`（1000ms）を超えたら落ちる。あわせて
「紙が画面の切り替わりまでにめくり終わる」も実際の段取りで見る — ページは表紙より
遅れてめくれるので、段を詰めるとここが先に破れて「紙が途中で消えた」ように見える。

## 35. 瓶の語は「どの問いから出たか」を連れて歩く

「ジャーナルポットの中に見えている言葉が、何を指すのか推測しづらい」という実機レビュー。

語は発酵の結果であって、それ単体では文脈を持たない。**触れたときに出どころの問いを返す**
のが、いちばん短い説明になる（`StudyWordTooltip`）。

そのために `words: string[]` を `words: StudyWord[]`（語 + 問い）に変えた。語だけを渡すと
出どころは**後から復元できない** — 同じ語が別の問いから出ることがあり、瓶の中では
重複を畳んでいるため。畳むときに、先に出てきたほうの問いを出どころとして憶える。

- 問いの文言は受信箱が `/questions` を引くついでに配ってくれる。ここで引き直さない
- 問いが消えていても**語は落とさない**。消された問いから出た語でも、瓶の中で発酵した
  ことに変わりはない（出どころを出せないことだけを伝える）
- 憶えてある書斎（localStorage）は形が変わるので `CACHE_VERSION` を 3 へ。
  古い形（語だけの配列）が残っていると瓶を組むところで落ちるので、検証も足した

### 語は的より先に当てる

瓶の的（hitbox）は語を丸ごと覆っている。的を先に見ると、語には**決して触れられない**。
レイキャストは語のスプライトを先に見て、当たったらそこで打ち切る。

押したときも同じで、語を押したら瓶は開かず出どころだけを見せる。瓶を開く道は
硝子の空いているところと、`JAR` のラベル／ピルに残っている。

### 「触れていなければ何も出さない」は検証ハーネスに乗らない

描画物が無い＝契約ノード（`data-verify-unit`）も出せないので、孤立検証の土台が
成立しない。ここだけ素の単体テストで見る（`study-word-tooltip.test.tsx`）。
出ているときの中身は検証スペックが見る。

## 36. サイドバーが持っていた `/questions` への道を、書斎が返す

「問いの変遷・一覧がどこからも見られない」という実機レビュー。

問いの**追加と編集**は瓶の中でできる（PC は `JarView`、SP は瓶の下端の「問いを整える」）。
できなくなっていたのは **いつ・どう変わってきたか** を見ることで、それは
`/questions` の `QuestionTimeline`（更新日でまとめた時系列）にしかない。サイドバーを
外したので、そこへ行く道が消えていた。

瓶の画面の右上に導線を置く（左上は「書斎へ戻る」の席）。**瓶の画面そのものには触れない** —
出し分けは `(protected)/layout.tsx` が行う。今回変えるのはナビゲーションと入口だけ、
という前提を守るため。

**PC だけに出す。** SP の瓶には下端に「問いを整える」があり、そこから同じ画面へ入れる。
右上にもう 1 つ置くと、同じ行き先の入口が 2 つ並ぶ。

> 残っている差: SP の問いの画面（`SpQuestions`）は提案 / 進行中 / 終了の平らな一覧で、
> PC のような**日付でまとめた時系列**を持たない。SP の変遷は別途。

## 37. 黙っている的を作らない — PC の棚にもラベルを出す

「積み重なった手帳やブックスタンドを開けば過去のエントリーに行けるのに、その動線が
分かりづらい」という実機レビュー。

原因は単純で、**PC では棚（ARCHIVE）のラベルだけ出していなかった**。当初の理由は
「ホバーすれば背表紙のツールチップが出るから」。しかし **ホバーは、そこに何かがあると
知っている人にしか効かない**。瓶・手帳・板が名乗っているのに、過去の記録を全部
持っている棚だけが黙っていた。

- `PC_LAYOUT.labelAnchors.archive` を与える（机の面 y ≈ -1.14 の、棚より少し手前）
- `PcLabels` が並べる的に `archive` を足す（配列から漏れていた）
- 検証は「PC では ARCHIVE を出さない」を裏返し、**4 つの的すべてが名乗る**に変えた。
  黙っている的をもう作らないための歯止め

背表紙のホバーで出る月と件数のツールチップはそのまま。ラベルは「そこに何かある」を、
ツールチップは「何が入っているか」を担う。

## 38. 用語を 1 つに揃える（`docs/glossary.md`）

「ジャーナル / エントリー / スタディジャーナルのどれで通すのか」という実機レビュー。

調べると**英字ラベルは矛盾していなかった** — `JOURNAL`（書く場所＝手帳）と
`ALL ENTRIES`（その中身の 1 件ずつ）は包含関係で、同じ画面に並んでよい。割れていたのは
**日本語の本文**で、書斎が「記録」、既存の一覧・エディタが「エントリー」を使っていた。

1 件を指すときは**エントリー**で通す。正は `docs/glossary.md`。

**語を機械的に置換しないこと。** 「記録」は別の意味でも使っている
（`連続記録`＝続いた日数、`L.A.B.による観察記録`、`問いが変化してきた記録`）。
置き換えたのは 1 件の記事を指す 5 箇所だけ。

### 検証で文言そのものを探さない

用語を直したら `SpElementSheet` の invariant が 2 本落ちた。`textContent` に
「もとになった記録」「無題の記録」が含まれるかで見ていたためで、**語を変えるたびに
検証まで壊れる**。`data-sources-heading` / `data-source-title` の目印で見るように直した
（書斎のキャプションでも同じことをした。§33）。

## 39. ホームで寄り引きできるようにする

「カメラワークに閉塞感・束縛感がある」という実機レビュー。

**周回はさせない。** 構図（机・瓶・板の位置関係）は設計の一部で、回せるようにすると
どの角度でも成立させるための作り込みが要る。近づく／離れるだけなら構図は保たれる。

- ホイール（PC）と 2 本指のつまみ（SP）で、注視点からの距離を 0.72〜1.35 倍
- **注視点は動かさない**。動かすと寄り引きが平行移動を兼ね、部屋の外へ出られる
- 上下限は狭く取る。引きすぎると部屋の外の何も無い空間が映り、寄りすぎると机の面
  だけになって行き先を見失う
- 効くのは**ホームだけ**。遷移中に効かせると着いた先のカメラと喧嘩して目的地がずれる
- つまんだ指を離した直後の `click` は「押した」と扱わない（瓶が開いてしまう）

## 40. 封を押したら、その手紙が開いた状態で瓶に入る

「データが届いた状態をビジュアルで表現したい（例: 瓶の上の手紙を押すと、最新の手紙を
開いた状態で瓶の画面へ）」という実機レビュー。

書斎の側は既にできていた — 手紙が届いていれば瓶の上に封が浮き、押すと
`/jar?letter=<発酵 id>` へ送る。**足りなかったのは受け取る側**で、`/jar` はこの値を
読んでいなかった。「届いた」ことを 3D で見せておいて、押した先で改めて探させるのでは、
封を出した意味が無い。

URL を読むのは page の仕事にして、**開き方は各端末の部品に任せる**（PC はサイドバー、
SP は円を開いてシート）。

### 「どの円がその手紙を持っているか」を知っているのは円だけ

PC は発酵の詳細を**円ごとに**引く（`useFermentationForQuestion`）。JarView 自身は
どの円がどの発酵かを持っていない。なので判定は円のラッパーに置き、自分の発酵で
なければ何もしない — 3 つのうち 1 つだけが反応する。

SP は逆で、受信箱が発酵 id と問い id の両方を持っている。そこで問いを引いて円を開き、
手紙そのものは中身を持っている `SpQuestionZoom` が組む。

### 合図は一度きり

開いたら合図（`pendingLetter`）を消す。残したままだと、**利用者が閉じた瞬間に効果が
再び効いて開き直り、閉じられなくなる**。テストでここを固定してある。

知らない発酵 id（URL を直に叩かれた・その後消された）では何も開かない。円は普通に出る。

## 41. 実機レビュー（2 巡目）: 机・鉛筆・本の厚み・語の当たり・席

### 画面から文字を落とす

下端に部屋の名前と発酵の状態（「手紙が届いています」等）を出していたが、「特に書く
必要もない、もう少しすっきりさせたい」と報告された。どちらも**物が既に語っている** —
部屋は見えているし、手紙が届いたことは瓶の封が伝える（未読の数字バッジを出さないのと
同じ理由）。キャプションごと落とし、`StudyChrome` は左上のマークと左下のアバターだけになった。

状態語（`status_*`）は他のどこからも使われていなかったので、i18n の鍵ごと消した。

### 鉛筆を押せるようにする

「置いてあるオブジェクトが基本的にクリッカブルな中で、鉛筆だけが存在として浮いている」。
押すと新しいエントリーを書き始める（積みの一番上と同じ行き先。物として最も素直に
「書く」を指しているのが鉛筆）。

- **当たりは物より大きく囲む。** 軸の太さは半径 0.055 しかなく、そのまま囲うと矢印でも
  指でも当たらない
- **ラベルは持たせない。** 積みのすぐ脇なので、`JOURNAL` の隣にもう 1 つ注釈が出ると
  どちらがどの物の名前か読めなくなる。代わりに触れたときだけ一言出す（`StudyHintTooltip`）

### 本の厚み — 上げるのは下限だけ

「本の中段と下段もクリック可能なエリアを増やしたい」。当たりの高さは厚みそのものなので、
薄い冊は帯が数 px しか無く、天板の縁と見分けもつかなかった。**物として厚くする**ことで
見た目と当たりが一度に直る（当たりだけ広げると、見えている冊の外を押せることになる）。

- 下限 0.1 → 0.2
- 1 件あたりの伸びは逆に 0.012 → **0.01 へ落とした**。同じ比で上げると、書いた月の冊が
  板のように分厚くなり、手帳ではなく発泡スチロールの塊に見える（0.016 で試して実際そうなった）
- 当たりの高さに積みの隙間（`STACK_GAP`）を足す。冊と冊のあいだに当たりの無い帯が
  残ると、そこを狙った指がすり抜ける

### 瓶の語 — 触れている語は止めて、大きくする

「結構押しにくい。ホバーしても今何がホバーされているのか分からない」。

- **触れている語は漂いを止める。** 動く的は、狙いを定めているあいだに逃げる。止めるのは
  その 1 語だけで、周りは漂ったまま（全部止めると瓶が固まって見える）
- 触れている語を 1.28 倍に。的（3D の物）のホバーは 1.02 だが、語は元が小さいので
  同じ比では気づけない

### 席はマークの実寸から導く

「ボード画面とエントリー画面で、左上のマークが既存の表示に被って押せない機能がある」。

原因は 2 つあった。**席（`--study-back-inset`）を手で決めた定数にしていた**ため、マークを
40px から 32px に縮めたときに席だけ別に詰めてしまい、席がマークより狭くなっていた。
そして**ボードはそもそも席を読んでいなかった**（`--sidebar-width` だけを見ていた）。

- 席はマークの外形（`BACK_MARK`）から導く。数字を 2 か所で持つと必ずずれる
- 中身を「マークの幅」から**絶対座標**に変えた。読む側は自前の余白に足すのではなく
  `max()` で比べる — 足すと、余白の広い画面ほど無駄に食い込む
- PC のボードの上部バーと SP のボードの日付にも席を読ませた

### 机に「机らしさ」を足す

「ズームアウトすると机がちゃぶ台のような少し質素なものに見える」。机の高さ（天板 -1.2 /
床 -2.9）は構図が依存しているので変えられないが、**下に何が詰まっているか**は足せる。
幕板・引き出し・板の脚を線で入れると、同じ高さでも「書き物机」として読める。
引き出しの箱を 1 つ置くのがいちばん効く。

### 旧ナビが残っていないかは、テストで見る

`test/architecture/old-navigation-is-gone.test.ts` を足した。部品はフラグ off のときのために
残るのでファイルは消えない — 消えているべきなのは「描かれること」だけなので、layout の
描画の分岐そのものを読み、旧ナビが layout 以外から描かれていないことも見る。

### `/study` を `/` にするのは持ち越し

「将来的にはルート（/）を書斎に切り替えたい」。`/` は今、メール確認の hash 受け・
未ログインの振り分け・既ログインのホーム送りを兼ねている（`HomeGate`）。書斎そのものを
ここへ移すと、その 3 つと 3D の読み込みが 1 つのルートに同居する。**別途**。

## 42. 実機レビュー（3 巡目）: 足したものを引く

PR #570 のコメント（`#issuecomment-5602873579`）。**前の巡で足したものが、そのまま
次の指摘になっている**回が 2 つある。ここはその整理。

### 机 — 足した構造を戻す

2 巡目で「ちゃぶ台のように質素」と言われて幕板・引き出し・板の脚を足したところ、
3 巡目は「現実的かつ具体的で稚拙に見える。抽象化されていたころのほうが、シンプルさが
想像をかき立ててエレガントだった」だった。**引き出しのような名前のある部品を線で描くと、
絵が説明的になって余白が消える。**

戻した。机は輪郭・手前の木端・前脚 2 本・木目 1 本だけに戻る。「質素に見える」は
**線を足して解く問題ではない**、というのがこの往復から出た結論で、`buildDesk` の
先頭にそう書いてある。

### 寄ると絵の上端が切れる — 注視点を寄りから導く

「ズームアウトから近づいてくるとき、画面の中心点が机の少し上部にあるため、ズームイン
していくとボードの上が見切れる。見切れるとき画面をグラブして上に持っていきたくなる」。

数字で確かめると、等倍の時点でボードの上辺は視野の縁ぎりぎり（PC で縦の半画角 22.5°
に対して 22.0°）にいる。注視点を据えたまま近づけば、**まっさきにここが外へ出る**。

`zoomTargetRise(layout, zoom)` を足した。`layout.camera.frameTop`（＝絵の上端。どちらの
構図でもボードの上辺）の**画面上の高さが倍率によらず変わらない**ように、注視点を縦へ
持ち上げる量を解く。カメラも同じだけ上がるので視線の向きは変わらず、寄るほど視界が
上へ動く — 利用者が手で引きたくなっていた動きを、寄り引きそのものに畳んである。

- 解は倍率の一次式になる（`camera.ts` の式を参照）。等倍で 0、引く側でも 0
- **横へは動かさない。** 動かせるようにすると寄り引きが平行移動を兼ね、部屋の外へ出られる
- テストは角度を焼き込まず、`frameTop` から解き直して「倍率を変えても同じ高さ」を見る。
  配置表を動かしてもテストが嘘にならないようにするため

### 瓶の外に文字を出すのをやめた

「瓶の言葉にホバーすると、瓶の中に出ている言葉と同じものがツールチップにも出て、同じ
内容が画面上に重複する」「瓶をクリックして瓶の画面に遷移しても、外側に出ていた言葉が
どこにあるのか分からない」「書斎の時点で瓶の外側に文字を出すこと自体が良い体験に
思えない」。

**なぜ出していたかというと、原案（`00-overview.md`）が「瓶の中で言葉が泡立つ」を
書斎の主役に据えていたから**で、1 巡目の「何を指すのか推測しづらい」への答えとして
出どころの問いをツールチップに足し、2 巡目の「押しにくい」への答えとして触れた語を
止めて 1.28 倍にした。足すたびに重複が増えていた。

外した。`StudyState.words` / `StudyWord` / `placeWords` / `StudyWordTooltip` /
`useFermentationKeywords` / `JarWord` と、語のためだけにあった i18n の鍵まで落としている。
**書斎で言葉に会う場所は瓶の中（`/jar`）の 1 つだけ**になり、書斎の絵と瓶の画面が
同じものを別の見え方で二重に持つことも無くなった。

副産物として、手紙 1 通ごとに詳細を引く往復（`/fermentations/:id`）が書斎から消えた。

### 瓶の上の封も外した

「瓶の上の手紙も、クリックできないうえ、手紙が届いたことの通知なのかどうかも
伝わりにくい」。押せること自体は §40 で直していたが、**伝わらない物を押せるように
しても伝わらない。**

利用者の判断で外した（「まずはスコープを小さくして、瓶に文字がない状態で、書斎上に
Jar・ボード・ジャーナル・アーカイブ・何らかの意味を付与したペンが配置されている状態に
絞ってしまってもいいのでは」）。書斎に置く物は**その 5 つだけ**になる。

- 封が唯一の入口だった `/jar?letter=<発酵 id>` も一緒に戻した（§40）。**入口の無い道を
  残さない** — 動くが誰も通れないコードは、次に読む人を必ず迷わせる
- `StudyTarget` から `letter` を落とした。作る側が無い variant を型に残さない
- 手紙が届いていること自体は消えていない。瓶の泡が静まり、ラベルの状態語が
  `pill_jar_letter` になる。**物を増やさずに、既にある物の様子で示す**

### 鉛筆の当たりが、鉛筆から 3 world unit 離れた場所にあった

「鉛筆はホバーしても何も起きません」。§41 で押せるようにしたはずだった。

`layout.pen` は**机（books グループ）のローカル座標**で、机は world で平行移動したうえ
y 軸まわりに -0.15 rad 回っている。ところが当たりだけ、配置表の値を world として
そのまま置いていた。PC では鉛筆の world 位置が `(5.54, -1.15, 2.28)` なのに、当たりは
`(2.55, -0.05, -0.1)` — 何も無い空中にあった。

位置も向きも**鉛筆そのものから取る**（`getWorldPosition` / `getWorldQuaternion`）。
箱の長辺は鉛筆のローカル y（＝軸の向き）に合わせ、姿勢ごと被せる。
**配置表の値を world として扱ってよいのは、その物が world 直下にあるときだけ。**

### 書斎に戻るときだけ絵が挟まる

「Back to study を押したときのロード中に謎の書斎アイコンが表示される。瓶をクリック
したときには出ないのに、戻るときだけ出るのは直感的ではない」。

1 巡目で「謎の 3 つの選択肢」を消したとき、絵は「これから出るものの予告」として
残していた。それが残りの違和感だった。

**出入りは対称でなければならない。** 書斎から出ていくときは溶暗だけで、絵も文字も
割り込まない。戻るときも同じにする — three.js を読み込んでいる数百 ms は利用者に
とって「戻っている途中」でしかなく、そこに別の絵を挟むと 1 画面増えたように見える。
`StudyFallback` は `loading` のとき地の色だけを描く。WebGL 非対応のときの絵と 3 つの
行き先はそのまま（あちらは「書斎が**出せない**」という別の意味を持つ）。

## 43. 出口を「物」から「動作」へ — 引き切ったら部屋へ戻る

左上に固定した「書斎へ戻る」が筋が悪い、という指摘。**入りが寄りなのに、出だけボタン**
だったのが噛み合っていなかった。瓶へは左へパンして寄り、板へは正対して詰め、手帳は
見開きへ寄って入る。ボタン・サイドバー・パンくずは「画面が並んでいる」前提の道具で、
1 つの空間を寄り引きしているこの体験とは語彙が合わない。

### 出は「同じ軸の逆」

キャンバスは最小倍率（`MIN_SCALE`）で頭打ちになる。**そこから先の引きは行き場が無い**
ので、その余りを捨てずに「部屋へ戻る力」に回す。

- `lib/canvas` が `OVERZOOM_OUT_EVENT` を投げる。**何に使うかはここでは決めない**
  （`lib/` はドメインを知らない）。bubbles で上げ、拾う側が決める
- `PullBackToStudy` が拾って、引いたぶんだけ部屋を滲ませ、引き切ったら `/study` へ
- 板と瓶の画面そのものには触れていない。重ねるのは `(protected)/layout.tsx`
  （features/pc/board → features/shared/study は reach-slice-isolation にも当たる）

**可逆であることが肝。** 手を止めれば滲みは引いて戻る。戻れると分かっているから
「ちょっと引いてみる」が試せて、そこで発見される — 使い方を説明する場所がどこにも
無い体験なので、ここが唯一の入口になる。

重さは `PULL_BACK.gain`。0.9（最小からさらに 3 倍ぶん）ではトラックパッドを 1 度
弾いただけで部屋が変わり、**「引いてみる」より先に離脱**した。0.45（7 倍ぶん、実測で
0.5〜0.7 秒の引き続け）にしてある。**この 1 つの数字は実機の手で詰め直す価値がある。**

### 部屋は消えたのではなく、遠くなっただけ

滲ませる絵が要る。3D を裏で回し続けるのは高い（WebGL のコンテキストは数えるほどしか
持てない）ので、**出ていく直前の 1 枚を掴んで持つ**（`backdrop.ts` / sessionStorage、
960px の JPEG で約 30KB）。

- 掴むのは `goTo` の頭＝**カメラが動き出す前**。遷移の途中で掴むと、既に瓶や板へ
  寄ったあとの絵になり、「戻ってきたときに見える部屋」にならない
- 描画の**直後**でなければ掴めない。`preserveDrawingBuffer` を立てていないので、
  別のタイミングで `toDataURL` を呼ぶと真っ白が返る
- 480px では部屋に見えなかった。書斎はほぼ白地に細い線だけで出来ていて、縮めると
  まず線が消え、「画面がうっすら曇った」だけになる。ぼかしも同じ理由で 10px → 3px

### 読み込み中に出すものが変わった

§42 で「読み込み中は何も描かない」にしたが、**悪かったのは描くことではなく、別の何かを
挟むこと**だった。3 つのリンクも、書斎を模した絵も、どちらも割り込みとして読まれた。
憶えた 1 枚を薄めずに敷けば、割り込みではなく**まだ遠い部屋**になり、three.js が来たら
同じ位置に本物が重なる。憶えていない（初回・別タブ）ときだけ地の色のまま待つ。

### 残っている穴

- **エントリー画面には効かない。** キャンバスを持たないので引きの軸が無い。入りが
  「表紙が開いて見開きへ寄る」なので、出は「本文の先頭でさらに引くと表紙が閉じる」に
  なるはずだが、それはあの画面そのものを触る話になる
- したがって**左上のマークはまだ外せない**。3 画面すべてに引きの出口が揃ってから

## 44. 左上をやめる — 出口は下端の縁ひとつ

§43 で引きの出口を作ったので、押す出口も引きの双子として作り直し、**左上の固定マークを
やめた**。

### 席を配るのをやめた

左上は 3 巡すべてで指摘された場所で、直し方も毎回同じ ―「画面の側に席を空けさせる」
（`--study-back-inset` / `--study-back-drop`）だった。席を読む場所は 7 か所まで増え、
**読み忘れると黙って重なる**。実際 3 回忘れられている（ボード、ロード中の枠、SP の
タイトル行）。左上はどの画面も自分のヘッダーに使いたい場所で、そこを共有物が占め続ける
限りこの往復は終わらない。

変数も、読んでいた 7 か所も消した。**被さりようが無くなったので、規約が 1 つ減った。**

### 下端の縁の中央へ

置ける場所は実測で選んでいる（1440×900）。左右の下隅はどの画面も使っている
（ボードと瓶は倍率とミニマップ、エントリーは保存状態と文字数）。中央も少し上には
浮かぶ操作パレット（エントリー 814..876）とツールバー（ボード 810..860）がいる。
**空いているのはいちばん下の縁だけ**で、そこに 46×21 で寝かせた（y 879..900）。
どの画面とも重なっていないことを実測で確かめてある。

- 名前は**横**に開く。縦に伸ばすとパレットの底に触る
- 常時は 45%、触れたときだけ濃くなる。引きが主で、これは「そういえば押しても戻れる」
  を担保する側なので、主張は控えめでよい

### 山形には横線を足す

エントリーの操作パレットは**すぐ上**にいて、その右端が「パレットを畳む」の山形を

足して「ここから下へ抜ける」にした。

あちらは開くと z-[70] の層を敷くので、下端の 21px がその上に残る可能性がある。

## 45. ラベルは名前しか言わない — 中身はホバーが言う

実機レビュー: 「ボードにホバーした時に何も出ないのはどうにかしてほしい。ボードの方も
『何件の写真』『何件のスニペット』みたいな感じにするとか」。あわせて
「ジャーナルではなくて、『エントリー』っていう名前にしてほしい」。

### 黙っていた的は 2 つあった

ホバーで何かが出るのは、手帳と背表紙（`StudyTooltip` — 月・件数・日付範囲）と
鉛筆（`StudyHintTooltip` — `エントリーを書く`）だけだった。瓶と板はラベルを持って
いるので「押せる」ことは伝わるが、**ラベルは名前しか言わない**。`BOARD` と出ている
だけでは、開くまで中に何が貼ってあるか分からない。

`HitEntry.hint` を鉛筆専用（`'pen'`）から `'pen' | 'jar' | 'board'` に広げ、文面は
`hints.ts`（純関数）が状態から決める。棚と手帳には付けない — 月ごとの紙が別に出るので、
同じ場所に 2 枚重なる。

| 的 | 出す言葉 |
| --- | --- |
| 瓶 | 未読があれば `未読の手紙があります`。無ければ `空` / `発酵中` / `もうすぐ` と同じ段階分け |
| 板 | `写真3件・スニペット12件`。**0 の種類は読み上げない**（「写真 0 件」と数えない） |
| 鉛筆 | `エントリーを書く`（従来どおり） |

瓶は届いた手紙を最優先で言う。溜まり具合は液面が見せているが、「手紙が届いた」ことは
見た目では言えない（泡が静まるだけ）。

### 内訳を数えるために、数え方そのものを直した

`countByUserId` は `head: true` の**行数**だった。ところが同じ付箋は daily と weekly の
両方に置かれることがあり、壁に描く側は `refId` で畳んでいる。つまり
**「12 枚」と名乗りながら壁には 9 枚しか無い**ことがあり得た（usecase のコメントは
「数えるほうも同じ基準にする」と書いてあったのに、実装がそうなっていなかった）。

`countPinnedByType` は `card_type` と `ref_id` だけを運んで畳んでから数える。
運ぶのは短い文字列 2 つで、1 人ぶんの実測上限は数十枚（Supabase 実測: 940 枚 / 55 人、
最大 61 枚）。`total` はその和なので、壁の枚数と必ず一致する。

### `JOURNAL` → `ENTRIES`

3D の手帳に貼る注釈だけを変えた。用語としては「手帳＝書く場所、エントリー＝その 1 件」
で割れていない（`docs/glossary.md`）が、**押した先はエントリーの画面**なので、
ラベルだけが別の語で名乗っていた。内部の識別子（`LabelKind` の `journal`、i18n の
`label_journal`、`journal-new` / `journal-month`）は手帳のままにしてある。

## 46. 出口は「浮かせて重ねる」のをやめて、帯にした

実機レビュー: 「『問いを紐付ける』を押して 2 つ以上紐付けたときに、『書斎に戻る』の帯と
重なってしまう」「エントリー画面でもう少し帯っぽくして、画面上に残すような形にしても
いいかもしれません」。

### 置き場所を 4 回変えて、やっと構造の話になった

左上のマーク → 下端の中央 → 上端の中央（浮かせて重ねる）→ **上端の帯**。

最初の 3 つは全部「浮かせて重ねる」で、違いは座標だけだった。だから毎回、**その座標に
何かが伸びてきた瞬間に破れる**。左上はヘッダーの見出し、下端は掴んで動かせるパレット、
上端の中央は問いのチップ（左から伸びて中央に届く）。

帯は座標の工夫ではない。画面がそのぶん下がるので、**重なりようが無い**。

### 下げ方は変数 1 本

`--study-exit-band` をシェル（PC は `<main>`、SP は外側の箱）が配る。読むのは 2 か所:

| 読む側 | 読み方 |
| --- | --- |
| 流れの中の画面（瓶・ボード・一覧・アカウント） | シェルの `margin-top` |
| `fixed` の画面（エントリーのエディタ） | `.sidebar-anchored { top: ... }` |

**`padding` ではなく `margin`。** padding だと箱の位置が動かないので、`absolute inset-0`
で敷いている画面（PC の瓶・ロード表示）は帯の下へ潜る — 絶対配置が基準にするのは
padding box の**外側の縁**だから。margin なら箱ごと下がり、`absolute inset-0` も
`h-full` も揃って従う。

`fixed` はどちらでも下がらないので、もう 1 本が要る。`--sidebar-width` が
同じ形で配られているので、読む側の作法もそれに合わせた（`.sidebar-anchored` は
もともと左をこの方式で決めている）。

**7 か所に席を配った `--study-back-inset` とは別物**である点に注意。あれは各画面が
自分のヘッダーの中で避ける形で、読み忘れると黙って重なった。こちらは画面が丸ごと
下がるので、読み忘れると**帯の下に潜る**＝すぐ目に見える。

### 重なり順は 55（パレットより下）

一度、下端に帯を生やしたときに「アクションパレットを閉じると帯の裏に隠されて復活
できなくなる」を出している（A 案・`e8a99d85` で撤回）。掴んで動かせるものより下に
置けば、最悪でも帯の名前が隠れるだけで、動かせば戻る。

## 47. 戻ってきた直後の「カクカク」は、部屋を 5 回作り直していた

実機レビュー: 「書斎の画面に戻ったとき、画面上でロードする関係で、一度止まった状態から
カクカクっと動くことがあります」。

書斎の状態は 5 つの取得を束ねたもので、**それぞれ別々に届く**。`StudyState` は届くたび
新しい object になり、`StudyCanvas` の `useEffect([state])` がそのたびに `setState` を
呼び、`applyState` が毎回 `disposeContent` → `buildContent` していた。1 回の作り直しは
ジオメトリとテクスチャの生成をひととおり含むので、そのフレームは必ず落ちる。

しかも憶えてある書斎（`stale-cache`）を敷いているときは、あとから届く本物が前回と
同じ内容であることがほとんどで、**その作り直しは絵を 1px も変えない**。

`contentSignature`（純関数）が「絵に出るもの」だけを 1 本の文字列にする。`buildContent`
が実際に読むのは 4 か所だけ（`notebooks` / `now` / `fermentation.readiness` と `.status` /
`board.cards`）で、`entries` と `questions` は絵に出ない。同じなら値だけ受け取って
物はそのまま。

## 48. 同じ口を 2 回叩かない — GET を短いあいだ憶える

実機レビュー: 「瓶の画面も開くたびにロードされているようで、表示されるまでに結構
タイムラグがあります」。

数えてみると、瓶を開くだけで同じ口が二重に叩かれていた。

| 口 | 叩く側 |
| --- | --- |
| `/api/v1/fermentations` | シェルの受信箱（`use-unread-letters`）と 発酵履歴（`use-fermentation-history`） |
| `/api/v1/questions` | 瓶（`use-jar-questions`）と 書斎の受信箱（`use-fermentation-inbox`） |

そのうえ、書斎 → 瓶 → 書斎 と行き来するたびに全部を取り直していた。

`createApiClient` に GET の憶えを持たせた（30 秒・このログインセッションのみ・
保存しない）。**憶えてはいけないもの**のほうが要点で、そこはテストで固定してある:

- 認証の口（`/api/v1/auth/*`）は憶えない — 失効に気づけなくなる
- 失敗した返事は憶えない
- JSON でない返事は憶えない（本文を text にして貯めるので壊れる）
- 書き込み（POST/PATCH/DELETE）は憶えを**全部**捨てる — どの口の答えが変わったかは
  lib からは分からない（分かろうとするとドメインを知ることになる）

同時に出た同じ GET は 1 本に畳む。受信箱と履歴が同じフレームで発酵一覧を見に行くので、
これだけでも往復が 1 回減る。

## 49. 帯は「見える帯」に、エントリーは下げずに流す（§46 の PC 側を撤回）

実機レビュー: 「書斎に戻るのボタンは帯にならないんでしょうか？ 何も変わってない気が
する」「全然帯になってないし、目立たないところにあります」。エントリーについては
「設定と日付と問いの行をただ下にずらしているだけ。クリエイティブではない。例えば
問いを選択した後に一定のエリアの中でスクロールさせるとか」。

### §46 は構造だけ帯で、見た目は前のままだった

§46 の帯は地がページと同じ色で、境目の線も引いていなかった（「帯として主張させない」）。
結果、見えるのは前と同じ 9px の名前だけで、変わったのは**画面が 34px 下がったこと**
だけ。依頼は「もう少し帯っぽくして、画面上に残す」だったので、主張させないのは
依頼と逆だった。

### 帯とタブ

全幅の帯に高さを持たせると、画面を下げるか画面に重なるかしかない。そこで高さを持つのは
**中央のタブだけ**にした。

- 上端いっぱいに 3px の帯（「ここは書斎の中の一室」）
- 中央からタブが垂れる（「ここを押せば戻れる」）。156 × 28px、名前は 12px
- 地は書斎のラベルの点の色（`#A8A381`）を溶かしたもの。ページの地からはっきり浮く
- 矢印は付けない（「矢印と文字の組み合わせが、どこにも出てないデザイン言語」）
- 触れるとタブが 3px 伸びる

### PC は下げない。中央だけ空ける

`--study-exit-reserve`（タブの幅 + 左右 16px）をシェルが配る。読むのはエントリーの
ヘッダーだけで、ヘッダーを `1fr | reserve | 1fr` の 3 列にして真ん中を空けた。
ボード（日付は左端・表示単位は右端）と瓶（問いの変遷は右上）は元から中央を使って
いない。

`.sidebar-anchored` の `top` と PcShell の `margin-top` は外した（PC ではもう下げない）。

### 問いは決まった幅の中で流す

左の列は `1fr` なので、何本結んでも中央へは届かない。流れていることが見えないと、
隠れた問いが「無い」ことになるので:

- **あふれている側の端だけを霞ませる**（マスク 24px）。続きがある向きが分かる
- 縦のホイールを横に回す（マウスには横のホイールが無い）。トラックパッドの横スワイプは
  そのまま通す
- いま結んだ問いを見える位置まで送る（列の外に生まれると、押したのに何も起きなかった
  ように見える）

「+n」に畳む案は取らない。畳んだ数字からは、どの問いを結んだのかが分からない
（`QuestionChip` の既存の判断）。

### SP だけは下がる

SP のヘッダーは題を中央に置くので、タブの真下に題が来る。SP だけはタブの高さ（28px）
ぶん画面を下げる（`--study-exit-band`、margin で）。

### 瓶のツールチップ

読み終えた手紙しか無いときの「読んだ手紙が入っています」は「手紙を読み返せます」に
した。状態の報告にとどまっていて、押すと何が起きるのかを言っていなかった。件数は
出さない — 受信箱は問いごとに最新 1 通しか持たず、数えると実際より少なく名乗る。

## 50. スマホの実機レビュー: 閉じる・下端の道具・語・円の中身、PC ボードの開閉

### 「閉じるボタンがない」は、在っても見えていなかった

SP の重ねる画面（問いの拡大・要素のシート・抜き書きのシート・問いの一覧）には
どれも閉じる操作が**在った**。ただし 4 か所とも 12px の灰色の文字（`--date-color`）で、

「モーダルを前提にスタイルを作らないで」の残り — 重ねる画面そのものをやめて行き先の
画面にする — は手を付けていない。閉じる操作が見えないことが実害として報告された部分で、
画面の作りを変えるのは範囲が大きい。

### 下端に浮かせない

SP ボードの道具箱は `absolute bottom-6` で盤面の上に浮いていた。盤面の下端のカードに
被り、指で掴めない。`SpBoard` を縦の flex にして、盤面を `flex-1`、道具箱をその下の
列に置いた。瓶の「問いを追加・編集」は元から流れの中にある。

### 語

| 前 | 後 | 理由 |
| --- | --- | --- |
| 抜粋 / 写真 | スニペットを作成 / 写真を追加 | PC のパレットの語に揃える。写真は「貼り付け」にしない（SP には貼り付けもドロップも無い） |
| 問いを整える | 問いを追加・編集 | 押した先で何ができるのかを言う |
| 抜粋（瓶のシートの見出し） | スニペット | ボードと同じ語にする |

### 円の中身

淡い円の地の上に、半透明の白に白い縁のカードを置いていて、地と見分けがつかなかった。

- 抜き書き: 地を不透明（`--surface-raised`）に、縁を立てる。字は 11px → 12px、幅 92 → 104px
- 言葉: 白い縁を茶の縁に、字を medium に
- 外周の問い: 不透明度 0.7 → 0.9

配置（輪の半径と個数）は変えていない。実機を見ずに動かすと、重なりを別の場所に移すだけに
なりやすい。

### PC ボードのパレットを畳めるようにする

エントリーの操作パレットと同じ形。末尾の「∨」で畳み、本文領域の下端中央につまみが
残る。畳んだかどうかは位置と同じく localStorage に憶える（鍵は別）。

## 51. タブは淡く、集中モードでは消す。パレットは 1 つにする

実機レビュー: 「書斎に戻るをもう少し薄くして、注意を引きすぎないように」「エントリーを
書いているときに画面が真っ白になる演出で、書斎に戻るもちゃんと消えて、集中モードが
できるように」「ボードのアクションパレットがエントリーと同じように動かせて閉じられる
ように。つまり同じコンポーネントを使っていてほしい」。

### タブ

- 淡くした: 地 24% → 14%、縁 55% → 30%、字は `--fg` の 70%、上端の帯 36% → 20%、影も薄く。
  ページの地と同じ色には戻さない（§49 で「帯になっていない」と言われた版）
- **集中モードで消える。** エディタは書いている間、`useSidebarVisibility().setHidden(true)`

  なので、同じ `hidden` を読んで退く。新しい仕組みは足していない。消えている間は押せず、

### パレット

エントリー（`EntryActionPalette`）とボード（`BoardToolbar`）は別々に作られていて、
ボードには掴み手が無く、畳めず、ボタンの大きさも違った。前回ボードに畳む機能を**足した**が、
それでは「似たものが 2 つ」のままだった。

`components/ui/floating-palette.tsx` に殻を 1 つだけ置き、両方がそれを使う。

| 殻が持つ | 各画面が持つ |
| --- | --- |
| 掴んで動かす（`lib/use-draggable-surface`）・位置を憶える | 並べる道具 |
| 畳む・つまみ・畳み具合を憶える | 定位置の高さ（`dockBottom`） |
| 掴み手・面の見た目・ボタンとアイコンの寸法の段 | ツールチップ・押せない理由 |
| 消えている間のクリック透過 | 憶える鍵 |

エントリーのパレットにあった掴んで動かす処理の写し（`use-draggable-surface` と同じもの）は
消した。置き場が `components/ui` なのは、エントリーとボードは互いを import できない
（`reach-slice-isolation`）ため。

## 52. 今月の一覧を開けるようにする／範囲はどの冊でも出す／浮いたチップの面を揃える

実機レビュー: 「今月のエントリー一覧を見る方法が無い。積みの一番上を押しても、2 段目・
3 段目のように月で絞った一覧が出ない」「一番上でも一覧を出し、そこに『新規作成』を。直接
書きたければ鉛筆で」「3 段目と棚のホバーに期間が出ない（2 段目には出る）」。あわせて
「書斎に戻る・問いを紐づける・アクションパレット・瓶の現在の問いの、影・角丸・余白と色を揃えて」。

### 手帳はどの冊も一覧を開く

`notebookTarget` は当月だけ `journal-new` を返していた。いまはどの冊も `journal-month`。
書く入口は 2 つ: 鉛筆（`journal-new`、従来どおり）と、一覧の月を選ぶ行の右端の「新規作成」。
SP の ENTRIES のピルも当月の一覧を開く（「ピルは 3D の物本体と同じ行き先」の約束どおり）。

### 範囲はサーバーが数える

ホバーの範囲を**手元の直近 20 件**から作っていたので、20 件より古い月（積みの 3 段目・棚の
背表紙）は範囲が出なかった。しかも `iso.slice(0, 7)` で **UTC の月**に切っていた。

月ごとの件数（`countByMonth`）がもともと全件を読んでいるので、そこで最初と最後の日も
取るようにした（`MonthlyEntryCount.first/last`）。日の切り方は `localDateKey` で、
`localMonthKey` と同じ（ずれると範囲の端が隣の月の日付になる）。Postgres の関数では
なく TypeScript で数えているので、migration は要らない。`monthDateRange` は消した。

### 浮いたチップの面

`surface.ts` に `ELEVATED_SHADOW` / `ELEVATED_RADIUS` / `ELEVATED_CHIP_*` を置き、
書斎へ戻るタブ・エントリーの問いのチップ・瓶の「現在の問い」がパレットと**同じ値を参照**する
（数字を写すのではなく同じ定数）。

- 地・縁・影・角丸（16px）・字の色はパレットと同じ
- ホバーは地が沈むだけ（パレットのボタンと同じ白に黒 5%）。瓶のチップの持ち上げと、
  タブの伸びはやめた — `surface.ts` の「動きはホバーの言語にしない」に揃う
- 結んでいる印（◦）にだけ accent を残す。瓶のチップの明朝は残す（書体は依頼の外）
- 問いのチップは横に流す箱の中にあるので、上下に余白を持たせて影が切れないようにした

## 55. 書斎ホームを既定で全員に出す

オーナーの判断: 「環境変数をオンにしなくても、全部書斎モードにしたい」。

E2E は既定の書斎を前提に直した: ログイン後の行き先は `/study`、サブ画面の「書斎に戻る」で

## 56. 書斎をルート（/）に置く

オーナーの判断: 「`/study` に行かなくてもいい。ルート自体が書斎になればいい」。

- 書斎の画面を `app/(protected)/page.tsx`（`/`）に移した。古い `/study` は `/` へ転送する
  （`next.config.ts`。`?study=on` などの query はそのまま付いていく）
- `/` は以前、保護レイアウトの外にある振り分けだけのゲート（`HomeGate`）だった。
  その仕事は次のように引き継いだ:

| 以前の `/` の仕事 | いま |
| --- | --- |
| メールリンクの hash（トークン） | 保護レイアウトの `useRootHashHandoff` が保存し、`/` を読み込み直す |
| メールリンクの hash（期限切れ・使用済み） | 同じ hook が確認画面（`/auth/confirm`）へ回す |
| 未ログイン → `/login` | 保護レイアウト（元からある） |
| 既ログイン → ホーム | `/` が書斎そのもの。書斎を止めていれば `/entries/new` へ |

**hash はログインへ送る判断より先に読む。** hash はサーバーに届かないので、ブラウザでしか
読めない。保護レイアウトの「未ログインなら /login」が先に走ると、hash ごと捨てられる。
hook を呼ぶ位置を redirect の effect より前にし、引き継ぎ中はログインへ送らない。

### 見つけて直した不具合: メール確認のあとログイン画面へ戻される

`use-email-confirm` はトークンを保存してから **アプリ内の遷移**で `/` へ送っていた。
認証（`AuthProvider`）はマウント時にしか復元しないので、保護画面に入った時点では
「未ログイン」に見え、ログイン画面へ戻される。OAuth の完了はすでに全画面遷移にしてあり
（同じ理由がコメントに書いてある）、メール確認だけが取り残されていた。全画面遷移
（`window.location.assign`）にした。E2E はこの直後に `page.goto` で読み込み直していたので、
この戻されを見逃していた。

## 59. SP の「書斎に戻る」は下端の帯に載せる

スマホのレビュー: 「書斎に戻るボタンは bottom のあたりに置いて欲しい」。あわせて、上端に
置いていたころの帯（画面を 32px 下げたぶん）は素の地色で境界が無く、タブが空中に浮いて
見える、という指摘があった（§57 で 3px の帯を外した後の状態）。

- `BackToStudy` に `placement`（`top` / `bottom`）を足した。端末の判断は
  `(protected)/layout.tsx` が持ち、PC は `top`（従来の垂れるタブ）、SP は `bottom`。
  `features/shared` の中で端末を見ない（`shared-no-device-detection`）ための prop
- 下端は**帯ごと**置く。帯はデザイン言語の「沈んだ面」（`--surface-sunken` + 上に
  `--surface-sunken-border` 1 本）。高さは `SHELL_ROW_HEIGHT`（48px）+ safe-area で、
  チップ（156×32、パレットと同じ面）はその中央に載る。上端のときに要らなかった帯が
  下端では要るのは、SP の画面の下端は瓶の「問いを追加・編集」・ボードの道具箱・
  エディタの発酵ボタンがどれも中央に居て、面を持たないチップを重ねると必ず被るため

### 瓶の線 — 塗りつぶしは出来ていた。輪郭が深度を無視していた

  面には polygonOffset が入っているので、面に乗った線は負けない
- LineLoop が最上段の左右を**弦**で結んでいた。口縁の近側 ±47° を結ぶ弦が口の中を横切って見える。
  上端も近側の弧で閉じるようにした（`silhouetteBufferSize` は弧 2 本分）

## 66. 読み込みの作法を 1 つに（先読み・骨組み・150ms の猶予）

実機の指摘（`docs/work/2026-09-13-sp-polish.md` D6・E4）。「問いの画面の読み込みが長い」「写真を貼るまで
何も起きない」。

- **待つなら形を先に置く。** 骨組みは `components/ui/skeleton` の 1 本。画面の形は各画面の
  `*-skeleton` が持つ。**150ms 以内に返るなら出さない**（`lib/use-delayed.ts` の `useDelayedTrue`。
  一瞬で返る取得にまで枠を出すと画面が一度揺れる）
- **取れるものは先に取る。** 瓶の地図は受信箱に手紙の id を持っているので、開いた時点で詳細を
  まとめて先読みする（`useFermentationDetails`）。以前は円を押してから一覧 → 詳細と 2 往復していた
- **押した瞬間に置く。** ボードの写真は、選んだ瞬間に仮のカード（ぼかした写真 + 脈打つ紙）を
  いま見えている真ん中へ置き、貼り終わったら実物と入れ替える。貼れなければ薄くして 4 秒残す
- 所要時間の実測（縮小・送信・署名 URL・VLM のどこが長いか）は実機と本番の回線でしかできないので
  未。長ければサーバー側の issue にする

### SP にエフェクトを出さない、と決めた理由

PC の視覚エフェクト（時間内包・圧力にじみ・消し跡・音量内包）はどれも本文の文字を span で包む
contentEditable 前提。SP の本文は `textarea`（画像を描けない代わりに IME と選択が素直）なので
成立しない。出すなら SP の本文を contentEditable に作り直す話になる。設定シートは本文の見た目
（書体・文字サイズ・行間・字間）だけにした。

## 68. PC の問い選択を SP と同じ選び手に、壜をもう一回り、hook の単体テスト

「スマホと PC で変えるべきではない」（作業指示 B5）を PC 側にも通した。

- **`QuestionSelectModal`（PC）の中身は `QuestionPicker`（shared）。** 以前はラジオ + `<select>` で
