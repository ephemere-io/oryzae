# 60 — 実装時の決着（仕様と実コードのズレ）

`00-overview.md` 〜 `50-rollout.md` は実装前に書かれている。リポジトリを読んだ結果、
いくつか前提が実際と違っていた。**このファイルが後から書かれた分だけ新しい**ので、
矛盾したらここを優先する。

## 1. `readiness` は上流に既にあった

`10-data-contract.md` は「上流にあるのは `FermentationSummary.status` だけ」としているが、
これは誤り。次のものが既にある。

| もの | 場所 |
| --- | --- |
| `readinessScore` (0..1) を返すドメインサービス | `fermentation-eligibility.service.ts` の `evaluateEligibility()` |
| それを組む usecase | `get-fermentation-readiness.usecase.ts`（admin から使用済み） |
| 永続化カラム | `user_fermentation_state.readiness_score numeric(3,2)` |
| 本人の SELECT を許す RLS | `supabase/migrations/00014_...sql` |

00014 のコメントに「readiness は admin ダッシュボード表示と **Jar アニメーションへの反映**を
意図する」と明記されており、最初からユーザーに出す前提で作られていた。

**決着: 案 A。** ただし新規実装ではなく、既存 usecase を本人向けに公開するだけ
（`GET /api/v1/fermentations/readiness`）。マイグレーション不要。

**案 B は採らない。** 案 B の式は `pickledSinceLastFermentation / threshold` だが、実際の
発火条件は `countCharsByUserIdSince()` ＝ *fermentation_enabled に関わらず全エントリの
合計文字数*。案 B は「サーバーの条件が変わると嘘になる」以前に、書かれた時点で既に嘘。

### 返す形

admin 版は `threshold` / `charsCurrent` / `hoursElapsed` まで返すが、本人向けは
`{ readiness, eligible, nextRunAt }` に絞る。「readiness を数値で出さない」方針
（`00-overview.md`「コピー」）と、閾値を晒さないため。

### `status` はサーバーから来ない

`StudyState.fermentation.status: 'idle' | 'fermenting' | 'completed'` は瓶の見た目の語彙で、
上流に 1:1 の対応が無い。サーバーの `FermentationStatus` は
`'pending' | 'processing' | 'completed' | 'failed'` で、しかも**発酵 1 件ごとの状態**
（ユーザーの状態ではない）。

**決着: クライアントで合成する**（`use-study-state.ts`）。

- `completed` … 未読の完了発酵がある。未読判定は localStorage にしか無く、**構造的に
  サーバーでは決められない**
- `idle` … 完了発酵が無く readiness が 0
- それ以外 … `fermenting`

## 2. `notebooks` は新設した

`GET /api/v1/entries/monthly-counts`。`created_at` は timestamptz、「月」はユーザーの
ローカル暦月なので、board API と同じ規約で `tzOffsetMinutes` を受ける
（これが無いと JST の月初 0–9 時の記録が前月に落ちる）。

実装は Postgres 集計ではなく「`created_at` だけを読んでサーバーで畳む」方式。
`user-me.ts` の `selectAllRows` と同じ id カーソルページングを使う（offset だと読んでいる
最中の INSERT でずれる）。行数が問題になったら RPC に差し替える — API 契約は変わらない。

**クライアント近似は不可。** 既存の `/entries?limit=20` から数えると 40 件の月が 20 件に
見え、手帳の厚みが嘘になる。

## 3. 「漂う言葉」は発酵中には存在しない

`fermentation_keywords` は `run-fermentation.usecase.ts` で `withStatus('completed')` の
直前に一括保存される。発酵は段階的な処理ではなく **LLM の 1 バッチ**なので、
`status: 'fermenting'` の間にキーワードは 1 件も無い。

`00-overview.md` の「readiness に応じて言葉が漂う／readiness が低ければ表示語数も減る」は
上流の作りと成立しない。

**決着: 直近に完了した発酵のキーワードを漂わせる**（＝いま漬けているものではなく、
前回の残り香）。追加 API は要らず、表示語数を readiness で絞れば「発酵が浅いほど語が少ない」
という見た目の規則もそのまま満たせる。

## 4. ファイル配置は `20-3d-component.md` と変えた

doc の配置は client の dep-cruise ルール 3 つに当たる。

- `shared-no-device-detection` … `features/shared/**` → `components/device-view` を禁止
- `reach-shared-purity` … `features/shared/**` → `features/{pc,sp}/**` を禁止
- `protected-pages-use-device-view` … `app/(protected)/**/page.tsx` に device-view を要求

また `scene/` を `features/pc/study/` に置くと `reach-slice-isolation` により
`features/sp/study` から import できず、SP 用に丸ごと二重実装になる。

**決着:**

```
apps/client/src/features/shared/study/
  types.ts                        StudyState など
  layout.ts                       PC/SP の座標・fov・尺度（端末名ではなく「配置」として持つ）
  constants.ts                    duration / easing / カメラ距離の唯一の置き場
  scene/                          three.js だけに依存する純関数（React 非依存）
    materials.ts jar.ts books.ts board.ts camera.ts labels.ts scene.ts
  hooks/use-study-state.ts
  components/study-canvas.tsx     layout を受け取る。端末を判定しない
  components/study-chrome.tsx
  components/entry-list-overlay.tsx
  components/study-fallback.tsx
apps/client/src/features/pc/study/components/pc-study.tsx   PC_LAYOUT を渡す薄い入口
apps/client/src/features/sp/study/components/sp-study.tsx    SP_LAYOUT を渡す薄い入口
apps/client/src/app/(protected)/study/page.tsx               ここで DeviceView 分岐
```

`study-canvas` には `device` 文字列ではなく `layout` オブジェクトを渡す。shared の中で
端末を分岐しないという規約に正直に沿うため。

## 5. SP のボードは**存在しない**

`app/(protected)/board/page.tsx` は `<DeviceView pc={<BoardView />} />` で `sp` を
渡していない。つまり SP でボードを開くと「スマホ未対応」が出る。

`30-branch-and-commits.md` のコミット 10「SP のボードから右ペインを外し、カードを
ドラッグできるように」は、実際には **SP ボードの新規実装**であって、規模が他の全コミットに
匹敵する。かつ「既存の board 画面は変更しない」という今回の縛りとも衝突する。

**決着: 当初は別 PR に分離したが、この PR で実装した。**
`features/sp/board/` に新設し、`/board` の `DeviceView` に `sp` を渡した。

- `sp-board-surface.tsx` — 見た目と指の操作（検証可能な純粋な描画）
- `sp-board.tsx` — 取得と初期フィット

PC の `BoardView` は触っていない。`reach-slice-isolation` により `features/sp` から
`features/pc` は import できないので、カードの描画は SP 用に別に書いた。とはいえ
コピーではない — PC が持つ意味的ズーム・選択・回転・リサイズ・ツールバー・ミニマップは
どれも無く、指の移動 1 つに絞ってある（`no-cross-device-duplication` の閾値 0.6 に対して
十分低い）。

**仕様との差: 位置を保存する。** `30-branch-and-commits.md` のコミット 10 は
「位置の永続化はしない（この段では見た目だけ）」としているが、`40-acceptance.md` は
「離した位置に留まる」と書いており、保存しないとリロードで配置が消える。PC が使っている
`useBoardSave`（debounce つき PUT）がそのまま使えるので、指を離した時に投げる。

**日の切り替えは付けていない。** 00-overview.md が SP について挙げているのは
「日付とカード枚数だけを隅に小さく浮かせる」だけで、日付ナビゲーションに触れていない。
そのため当日のボード固定になっている。過去の日を見る導線が要るかは別途の判断。

## 7. `--sidebar-width` も分岐対象

`00-overview.md` は「`<Sidebar />` と `marginLeft: SIDEBAR_WIDTH` を外す」としか書いていないが、
`(protected)/layout.tsx` が `<main>` に生やす CSS 変数 `--sidebar-width` は **board が読んでいる**

pointer-events を切るだけで `marginLeft` は残るので、書斎の全幅描画には足りない。

## 9. 残っている穴: 古い月の一覧が空になる

一覧オーバーレイは `useEntries`（`GET /api/v1/entries?limit=20`）が取ってきた
**直近 20 件**を月で絞っているだけ。そのため、20 件より古い月を選ぶと
「この月の記録はありません」と出る。

実機で確認した食い違い（2026-09-04 時点のテストアカウント）:

| 月 | 手帳／棚が言う件数 | 一覧が出す件数 |
| --- | --- | --- |
| 2026.09 | 6 | 6 |
| 2026.08 | 14 | 14 |
| 2026.04 | 1 以上（棚に背表紙がある） | **0** |

見出しも `2026.04 — 0 ENTRIES` と出るので、**手帳の厚みと矛盾した数字を自分で
名乗ってしまう**のが厄介。件数は `monthly-counts`（全期間の集計）から来るのに、
一覧は直近 20 件しか見ていない。

直し方は 1 つで、`GET /api/v1/entries` に月の絞り込みを足すこと
（`questionId` と同じ形の `month=YYYY-MM`。サーバー側は `localDayRange` と同じ
`tzOffsetMinutes` を受けて期間で絞る）。クライアントでページングを繰り返して
埋めるのは、月が古いほど往復が増えるので採らない。

今回のコミット群には**入れていない**。30-branch-and-commits.md のどのコミットにも
無い新しいサーバー変更で、入口の設計（過去月の手帳を押す）そのものに関わるため、
独立して判断・レビューされるべきだと考えた。机に積む直近 3 ヶ月は 20 件に収まる
ことが多く、棚（4 ヶ月以上前）を押したときに出やすい。

## 10. ⚠️ レビュー用の一時的な端末切替（マージ前に外す）

cookie（無ければ UA）から確定して `x-device` ヘッダで渡す作りなので、切り替えには
cookie の書き換えとリロードの両方が要り、レビュー中に DevTools の Console を毎回
開くことになっていた。プレビューで PC / SP を見比べる間だけの足場。

一時的なものだと見た目で分かるよう、枠を破線・テラコッタにしてある。

**外し方（3 箇所）:**

1. `apps/client/src/components/device-switch.tsx` を消す
2. `apps/client/src/app/(protected)/layout.tsx` の `<DeviceSwitch />` と import を消す
   （どちらにも `TODO(review):` を付けてある）
3. この節を消す

`git grep 'TODO(review)'` で 2 箇所とも出る。

## 11. 瓶の言葉は「問いごとの最新キーワード」を全部浮かべる（原案からの拡張）

原案は「直近に完了した発酵のキーワードを最大 6 語」だった。ここを広げて、
**設定している問いごとの最新のキーワードを全部**浮かべる。受信箱
（use-fermentation-inbox）が問いごとに最新 1 通へ畳んでいるので、その全部の詳細から
集める（問いは生存が最大 3 件なので往復も 3 回に収まる）。

語ごとの大きさは 0.72〜1.38 倍でばらす。**`Math.random()` では決めない** —
状態が更新されるたびにシーンを組み直すので、乱数だと大きさが毎回変わって画面が
ちらつく。語の文字列から決めるので、同じ語は常に同じ大きさになる。

大きさがばらつくぶん、行間は一律ではなく**隣り合う 2 語の高さ**から決める
（一律だと大きい語どうしが触れる）。全部が入らないときは行間を詰めて収め、
詰めても入らない語だけを落とす。

## 12. 完了した瓶の泡は「止める」から「ゆっくり上げる」へ変えた

仕様（`00-overview.md`「完了すると泡が止み」/ `21-3d-parameters.md`「完了時 0＝静止」）と
原案（`speedScale = done ? 0 : ...`）は、発酵が完了したら泡を**止める**と決めている。
そこだけ外している。

理由: 手紙が届いている瓶はいちばん長く見る状態で、そこで泡が完全に止まると
「壊れている」と読まれる（実機のレビューで 2 度指摘された。ロード中だけ泡が上がり、
データが届くと止まるので、なおさら不具合に見える）。

**静けさは失っていない。** 泡の数は 30 → 4 に落ちたままで、封も浮かぶ。速さだけ
readiness 0.12 相当のごく遅い流れにしてある。戻すなら `COMPLETED_DRIFT` を 0 にする。

## 13. 瓶の言葉は液面で頭打ちにしない

原案は言葉を「液面までの高さ」に収める。ここも外している。

readiness が低いと液面までの高さが 0.1 ほどしか無く、そこに収めようとすると
**2 語目以降が全部落ちて 1 語しか浮かばない**（実機でそうなっていた）。問いごとの
キーワードを全部見せる（§11）という指定と両立しないので、入り切らないぶんは瓶の
空いている高さへ伸ばす。上限は首がくびれ始める手前（2.35）で、コルクには重ならない。

液面に余裕があるときは従来どおり液面までに収まるので、発酵が進んだ瓶の見え方は変わらない。

## 14. 呼吸の周期は「1 秒」ではない（21-3d-parameters.md の注記が誤り）

`21-3d-parameters.md` は呼吸を「y に `sin(t) * 0.05`（1s）」と書いているが、
**式と注記が食い違っている**。原案の `t` は `Date.now() * 0.001` ＝ **秒**なので、
`sin(t)` は角速度 1 rad/s、つまり周期は **2π ≒ 6.3 秒**。1 秒ではない。

注記のほうを信じて 1 秒周期で実装したところ、カメラが毎秒上下して画面全体が
小刻みに揺れ、「マウスを動かしていないのに行きつ戻りつして気持ちが悪い」という
報告になった。振幅（0.05）は小さくても、周期が 6 倍速いと酔う。

同じ取り違えが言葉の揺れと周回にもあった。原案の係数はどれも **rad/s** で、
2π を掛けてはいけない。

| もの | 原案 | 周期 |
| --- | --- | --- |
| カメラの呼吸 | `sin(t)` | 約 6.3 秒 |
| 言葉の上下 | `sin(t * 0.3)` | 約 21 秒 |
| 言葉の周回 | `cos(t * 0.1)` | 約 63 秒 |
| 輪郭の呼吸 | `sin(t * π/2)` | 4 秒 |
| 封の浮遊 | `sin(t * 0.8)` | 約 7.9 秒 |
| 泡の横揺れ | `sin(t)` | 約 6.3 秒 |

輪郭・封・泡は最初から合っていた。ずれていたのはカメラと言葉の 3 つ。
`camera.test.ts` に「1 フレームあたりの変化が振幅の 2% を超えない」という
テストを置いてあるので、速くしすぎると落ちる。

## 15. 前回の書斎を憶えて、開いた瞬間に出す

書斎を開くたびに瓶の言葉とボードのカードを取り直していて、その間ずっと机と壁が空に
見えていた（発酵の詳細は問いの数だけ往復するので、いちばん遅い）。

`lib/stale-cache.ts` に stale-while-revalidate の器を置き、`use-study-state` が
取り終えた `StudyState` を localStorage に憶える。次に開いたときは**取得を待たずに
前回の絵を出し**、裏で取り直した本物が届いたら差し替える。取得そのものは止めていないので、
古い値が長く残ることはない。

決めごと:

- **鍵は利用者ごとに分ける**（`study:<userId>`）。端末を共有していると、前の人の
  記録の冒頭や発酵の言葉がそのまま出てしまう
- **ログアウトで全部捨てる**（`clearAllStaleCaches`）。ここには日記から作った内容が入る。
  接頭辞で自分の分だけ消すので、下書きや既読は巻き添えにしない
- **読むときに形を確かめる**。中身は前のバージョンの自分が書いたもので、信用して
  そのまま 3D へ流すと形が変わった瞬間に落ちる。版（`CACHE_VERSION`）と型ガードの二重で止める
- **日付だけは憶えた値を使わない**。日をまたぐと当月の手帳が前月として出る
- 認証 context はこの hook から読まない。読むと `AuthProvider` の中でしか動かなくなり
  単体で試せなくなるので、利用者は呼び出し側から渡す

## 16. サイドバーはサブ画面でも消す

当初は書斎ホームでだけ左サイドバーを外していたが、jar / board / entry でも外す。
書斎が「唯一のグローバルナビゲーション」（00-overview.md）である以上、行き先の画面にだけ
旧ナビが残るのは半端で、戻り道が左上のマークと左のサイドバーで二重になる。

これに合わせて `entry-editor` の左端を `SIDEBAR_WIDTH`（定数 80px）から
`var(--sidebar-width, 0px)` に変えた。定数のままだと、サイドバーを描かない画面で
左に 80px の隙間が残る。ボードのツールバーは元から同じ変数を読んでいる。

**SP のボトムナビも同じ条件で外す。** 当初は「消すと `/questions` へ行けなくなる」ため
残していたが、問いの入口を瓶の中へ移した（§17）ことで理由が消えた。判定は
`{!studyHome && <SpBottomNav />}`（サイドバーと同一条件）なので、**フラグ off の間は
従来どおり全画面に出る**。

## 17. SP の瓶は「壜のまわりを問いが回る」形にした（原案の範囲外）

`docs/oryzae-study/` は書斎ホームの仕様で、SP の `/jar` そのものは対象外だった。
ボトムナビを外すと問いへ行けなくなるため、PC の瓶と同じ「中央に壜、そのまわりに問いの円」
という構図を SP にも持たせ、問いの管理をそこから開くようにした。

**PC と違うところ（＝盤面を持たない）。** PC は問いの円を好きな場所へドラッグして置ける
「世界」だが、SP は片手で持つ縦長の画面で、置き場を作っても指で選び分けられない。
代わりに軌道の上へ等間隔に並べ、**横に払って回して選ぶ**。重ならないことが構造で
保証されるので、問いが増えても破綻しない。

決めごと:

- **回転は縦軸まわり**（横楕円に射影）。横軸まわりに回すと円が上下に散り、縦長の画面で
  壜と重なって読めなくなる。手前は壜の裾、奥は壜の首、と縦にずらして奥行きを出す
  （`features/sp/fermentation/orbit.ts`）
- **指を離しても止めない。** 0 まで減速すると「触るまで動かない置物」に見える。
  既定の速さ（`IDLE_SPIN`）へ戻す。`prefers-reduced-motion` のときだけ止める
- **回転は React の state ではなく DOM の style に直接書く**。60fps で state を回すと
  円の中の SVG まで毎フレーム差分計算に乗る。React に渡すのは「正面がどれか」だけ
- **回した直後の指離しで円を開かない。** `click` は `pointerup` の**後**に来るので、
  pointerup で「ドラッグ中」を降ろすと、回し終えた位置の円が開いてしまう。回したかどうかを
  次の click まで持ち越す（`SpJarOrbit/drag-does-not-open` がこれを固定している）
- **円の重なり順は軌道の中で閉じる**（`isolation: isolate`）。円は奥行きを z-index 0..1000 で
  表すので、層を閉じないと開いた円（z-20）やシート（z-30）を突き抜ける
- **問いテキストは畳んで、縮めない。** PC は円周に収まるまで字を小さくするが、SP で
  それをやると読めなくなる。読める大きさ（12–17px）を先に決めて、入らない分を「…」で
  畳む（`ring-text.ts`）。`textPath` は入らない分を黙って捨てるので、畳まないと末尾が消える
- **円の中では中身を読ませない。** 言葉・抜粋・手紙は「在ること」だけを示す押せる的で、
  本文はボトムシート（`SpElementSheet`）で読む。小さな円に本文を詰めると全部読めなくなる

## 18. 壜の絵を shared へ切り出した（PC の瓶にも影響がある）

SP の瓶にも「PC と同じ壜」を中央に置くため、`JarView` の中にあった壜の絵を
`features/shared/fermentation/components/jar-bottle.tsx` へ移した。**PC 側の DOM は
そのまま移設した**ので見た目は変わらない…はずだったが、2 点だけ実際に変わっている。

1. **中の言葉の切り抜きを比率指定に直した。** CSS の `clip-path: path(...)` は座標を
   絶対 px で解釈する。壜の絵は viewBox 480x600 を器に合わせて伸縮するので、器が
   480x600 から離れるほど絵と切り抜きがずれる。PC（500x620）ではほぼ一致していて
   気づかなかったが、SP（幅 240 前後）では切り抜きが壜の 2 倍になり、中の言葉が
   **壜の外へこぼれた**。`clipPathUnits="objectBoundingBox"` の SVG clipPath に変えて、
   器の大きさに依らず一致するようにした（`jar-path.ts` の `toUnitPath`）。
   PC でも数 px ぶん切り抜きが正確になる
2. **絵の器を viewBox と同じ比（480:600）に固定した。** 比が違うと SVG は余白を作って
   中央に寄る（preserveAspectRatio）ため、1 の切り抜きとずれる。PC の器は 500x620 で
   比が 0.806 だったので、描画は 496x620 になる（従来の "meet" 縮尺と同じ結果）。
   中の言葉は器の幅に対する比（`cqw`）で書くようにしたので、PC では従来比 1.03 倍に
   なる（480 → 496）。目視で分かる差ではない

## 19. 手帳が開く段取りの取りこぼし 3 件

実機で「1 ページしかめくれない / 右側にいつまでも表紙が出ている / 見開きが出てこない」と
なっていた。原案（プロトタイプ）と突き合わせたところ、原因は 3 つに分かれていた。

1. **表紙が 2 枚あった。** 静的な板（`coverSlab`）を全冊に敷いたうえで、当月だけ別に
   開く蝶番を重ねていた。開くのは蝶番の方だけなので、板は同じ場所に残り続ける。
   表紙とラベルは**蝶番の中だけ**に置く（原案も全冊が蝶番を持つ）。
2. **見開きの罫を紙（leaf）に引いていた。** 原案は**束の上面**（右の頁）と**表紙の裏**
   （左の頁）に引く。紙は薄い板でしかない。罫を紙に付けていたので、紙をめくり終えた先が
   白紙になり、「見開きが出てこない」ように見えていた。
3. **紙を下からめくっていた。** 原案は `leaves.slice().reverse()` で**上から**めくる。
   下からめくると、上に載っている紙に隠れて 1 枚しか動いて見えない。
   積み順 → めくり順の変換は `SPREAD_PAGES.turnOrderOf` に閉じ、テストで固定した。

あわせて**開く向きが逆**だったのも直した。蝶番は左端にあり表紙は右へ伸びているので、
`rotation.z` は**正**で持ち上がって左へ倒れる。負にすると机を突き抜けて下から回り込む。

`pageProgress` が `PAGE_FOLLOW` を使わず同じ数値を直書きしていたのも直した
（`constants.ts` の「数値をシーンのコードへ直接書かないこと」に反していた）。

## 20. 左上のマークはエディタの下に潜っていた

エディタは `fixed inset z-50`（ゴースト層が 51）で全面を覆う。`BackToStudy` は z-40 だった
ので、jar / board では見えるのに **entry だけマークがそもそも出ない**状態だった。

- マークを **z-55** に上げた（エディタより前・ドロワーやモーダル（60 以上）より後ろ。
  モーダルが開いている間はマークも一緒に伏せるのが正しい）
- ただし上げるだけだと、マークがエディタ左上の「新規」ボタン（PC）や ⋯ ボタン（SP）に
  重なって**押せなくなる**。席は画面側が空ける: `(protected)/layout.tsx` が
  `--study-back-inset` を配り、PC はツールバーと問いの行、SP はヘッダとタイトル行が
  その幅だけ左に余白を足す（`--sidebar-width` と同じ seam）。マークが出ていない間は 0px

マークの位置（`left-6 top-6` / 40px）は**書斎のブランドマークと同じ**にしてある
（`study-chrome.tsx`）。サブ画面のマークはそれが戻る導線を兼ねる、というのが 00-overview.md の
仕様なので、ここをずらして逃げない。

## 21. 瓶の言葉が「出て・消えて・また出る」ように見えていた

言葉（キーワード）は二段構えで取る — まず手紙の一覧、そのあと各手紙の詳細。
`useStudyState` の `loading` に**二段目を数え忘れていた**ため、一段目が終わった時点で
「取得済み・言葉ゼロ」になり、憶えていた言葉がいったん消えてから 1 秒ほどして戻っていた。

- `useFermentationKeywords` の `loading` を `useStudyState` の `loading` に含めた
- あわせて、その `loading` を **effect ではなく描画中に決める**ようにした
  （「いま持っている言葉が、いまの発酵の分か」を鍵の一致で見る）。effect が走ってから
  loading を立てる作りだと、一覧が届いた直後の 1 フレームだけ穴が開く
- 取り直している間も**前の言葉を返す**。空に落とすと、その間だけ瓶が空になる

書斎は state が変わるたびにシーンを**組み直す**（差分更新をしない）ので、この手の
「一瞬だけ空」はそのまま画面のちらつきになる。取得の段が増えたら `loading` に足すこと。
