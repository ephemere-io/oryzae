# 70 — 書斎の扉（ログイン・登録・認証の画面）

認証まわりの画面（`/login` `/signup` `/forgot-password` `/reset-password` `/callback` `/auth/confirm`）の
地を、**書斎の手前にある扉**にする。書斎と同じ線画・同じ紙と墨で描き、ログインできたら扉を押し開けて
奥へ歩き、地の色に溶ける。書斎は同じ地の色から現れるので、ログインの前後が 1 つの廊下の続きになる。

## なぜ

- それまでの認証画面は、白地に中央寄せのフォームだけの SaaS の定型で、書斎の世界と切れていた
- 書体が body 既定の明朝のままで、ラベル・入力欄・ボタンまで明朝だった（`design-language.md` §5 違反）
- Google でログインして戻った `/callback` に、認証レイアウトの言語選択（「日本語」の `<select>`）だけが
  ぽつんと浮き、誰も触る理由の無い画面になっていた

## 画面

| 状態 | 扉 | 紙（フォーム） |
| --- | --- | --- |
| 待っている | わずかに開いていて（`DOOR_ANGLE.rest`）、隙間から奥の格子と書斎の気配が覗く | PC は扉の右に 1 枚立てる / SP は画面の下に浮かせる（2 段。下記） |
| 送信中・認証中 | 取っ手に手を掛けたくらい開く（`waiting`）。失敗したら閉じ直す | そのまま |
| 入れた | 紙が退く → 扉を押し開ける → 扉の正面まで歩く → 書斎へ渡す（`enterPlan`） | 退く |

### SP の紙は 2 段

最初の版は PC と同じく全部を 1 枚に並べ、「紙が下にはみ出して『ログイン』が見切れる」
「扉が小さく正面向きで扉感が無い」と差し戻された（PR #624 の実機レビュー）。

- **選ぶ:** 名前・「Google でログイン」・「メールアドレスでログイン」・下端の一文だけ。扉は画面の半分以上を取る
- **入力中:** 左上の正円の「戻る」と入力欄・送信ボタン。下端の一文と登録枠の表示は省いて紙を短くする。
  開いた同じタップの中で最初の入力欄に focus を渡す（iOS はそうしないとキーボードを出さない）
- 判定は端末ではなく紙の置き方（`EntranceControls.compact`）。PC の紙と検証ハーネスでは常に全部を出す
- 紙は画面の下端に貼り付けず、**左右と下に余白を取って浮かせる**（角は 4 つとも丸い）。下端から
  せり出すシートに見えると、扉の部屋の上に別の画面が被さったように読める
- 中身が入れ替わる（選ぶ ⇄ 入力中、認証中 → 失敗）ときは、**下の余白と位置を据え置いたまま外枠の
  高さだけを寄せる**。`height: auto` は transition できないので、中身の高さを測って外枠に渡す

### 歩き着くのは敷居の手前。奥は近づくほど見えてくる

歩きの終点（`THRESHOLD_VIEW`）は**壁の手前**に置く。以前は敷居をまたいで奥まで抜けていて、
開いた扉板と枠がカメラのすぐ脇に来るため、最後の何コマかが**縦に走る線だけ**になった。
そのコマがそのまま書斎へ渡す 1 枚になるので、書斎が出るまで「柱みたいなもの」が画面に残る
（PR #624 の実機レビュー）。

- **扉が扉として読める距離で止める**（`THRESHOLD_VIEW.position.z > DOOR.height`）。寄りすぎると
  枠が画面からはみ出し、何を見ているのか分からない絵になる
- **着きで減速する**（`walkProgress` は `easeInOutCubic`）。止まった絵がそのまま渡す 1 枚になる
- **奥の書斎は近づくほど濃くなる**（`GLIMPSE_REVEAL`）。待っている間は「何かがある」までに留め、
  歩き出してから机・瓶・壁のボードが見えてくる。開口の中が空だと、残るのは枠の線だけになる
- テストは軌道そのものを見る（`door.test.ts`）。壁をくぐらないこと、後半はずっと開口の中を
  見ていること（`looksThroughDoorway`）

### 書斎へは、白く飛ばさずに渡す — 歩いている canvas ごとルーターの上に持ち上げる

扉をくぐった先で画面が一度地の色になり、そこから書斎が溶けて現れていた。「ホワイトアウトして
ブツ切れになる」（PR #624）から始まって、実機の計測と録画で 3 段階に直した。

1. **白が出る**: 間に挟まるものが多い。認証レイアウトが外れる → 保護レイアウトが mount →
   mount 前のロード表示 → 書斎の canvas を読み込む → 最初の 1 フレーム。どれか 1 つでも地の色を
   描けばそこが白い。段ごとにフェードを合わせても穴は残る → **ルーターの外（root layout の
   `StudyHandover`）に部屋を載せたままにする**ことで穴を無くした
2. **静止する**: 撮った 1 枚を敷いていたので、書斎が描かれるまでの 0.5〜1 秒が静止画だった
   （Google ログインは全ページ読み直しで 1 秒近く → `adoptSession` でアプリ内遷移に）
3. **カクッとする**: 歩きが止まって静止画に変わる瞬間と、静止画が別の動きで寄り始める瞬間で
   **速度が途切れる**。継ぎ目のあるものは、どう合わせても継ぎ目が残る

いまの形は継ぎ目そのものを無くす:

- **歩きは止まらない**（`glideView`）。目指す先（扉の開口の中、`GLIDE.target`）へ、残りの距離に
  比例した速さで近づき続ける。速度は常に連続で、着く前に書斎が現れる。読み込みが遅ければ
  ゆっくり近づき続けるだけ。歩き出しだけ助走を付ける
- **渡すのは写真ではなく canvas そのもの**（`EntranceSceneHandle.detach` → `study/handover.ts`）。
  扉の正面まで来たら（`walkMs`）、描き続けている canvas をルーターの上に載せ替えてから移る。
  認証画面が外れてもシーンは止まらない（cleanup は持ち出し済みなら dispose しない）
- **書斎の canvas が最初の 1 フレームを描いたら、上の canvas を溶かして捨てる**（360ms）。
  書斎の側も寄りながら現れる（`ARRIVAL`）ので、溶けるあいだも両方が動いている。
  合図が来なくても 4 秒で外す
- 扉から入ってきたときは書斎側の地（`backdrop`）を出さない（`StudyHome` の `throughDoorRef`）

撮った 1 枚（`captureRenderedFrame`）はもう扉では使わない。GPU の読み戻しと PNG の符号化
（3000×1700 で数百 ms）も消えた。書斎が出ていくときの戻り道の地は、書斎の側が撮る（従来どおり）。

扉が無いとき（WebGL 非対応）だけ、持ち上げるものが無いので `REDUCED_FADE_MS` で溶かす。
全ページ読み直しになる経路（`adoptSession` に載せられなかった時の保険）では canvas を持ち越せ
ないので、書斎のロード表示から始まる。

**測り方**: `/verify/handover`（プレビュー限定）で計測を始めてからログインし、戻って読む。
送信・扉・移る・mount・1 フレーム目の ms と、40ms 以上のコマ落ちが並ぶ。遷移を録画して
コマの差分を取るのも有効（静止したコマ＝差分 0 が続く／白飛び＝線の無いコマ）。

### 画面の高さは `svh` と `dvh` の小さい方（SP）

紙は画面の下に浮かせるので、**下のツールバーに隠れない**ことが要る。高さの下限は
`min(100svh, 100dvh)`＝**いま見えている高さを超えない**値にする。

- `svh` だけでは足りない。実機の Dia（iPhone 15 Pro）で測ると `100svh = 793` に対して
  `100dvh = innerHeight = visualViewport.height = 717` で、**`svh` の方が実際の表示領域より
  76px 大きい**。その分だけ紙が下にはみ出してツールバーの裏に入っていた
  （iOS には `svh` を画面の高さのまま返すブラウザがある）
- `dvh` だけにもしない。Safari では読み進めるとツールバーが畳まれて `dvh` が伸び、紙が動く
- `env(safe-area-inset-bottom)` にツールバーは現れない（Dia では 0）。当てにしない
- `visualViewport` も当てにならない。Dia は**ビューポート自体は正しく返していて**（717）、
  嘘をつくのは `svh` だけだった。JS で測る仕組みは入れない

`<body>`（`h-full` = ツールバーの裏まで含む大きい方のビューポート）いっぱいに伸ばさないこと
（`flex-1` を付けない）も引き続き要る。伸ばすと下端の紙がその底に着いてしまう。

実機で値を確かめたいときは、プレビュー限定の `/verify/viewport`（本番は 404）を開く。
そのブラウザが返す `innerHeight` / `visualViewport` / `svh` / `dvh` / `lvh` / `safe-area` と、
認証画面が使う `min(100svh, 100dvh)` が並ぶ。

### 紙の置き場は幅で変えない（PC）

画面幅で中央と右を切り替えていたころ、Brave では切り替えが効かず紙が中央に来て扉に被った
（PR #624 のレビュー）。PC の構図は扉が左・紙が右で一組なので、常に右端に置く。

### 扉は「見えている窓」に合わせて置く

SP の扉の構図は画面全体ではなく**紙の上の窓**に対して組む（`EntranceSceneHandle.setFrame`）。
窓の高さを測って渡し、scene は縦の画角をその窓に合わせ、`setViewOffset` で紙の下へ延ばす
（レンズシフト）。紙が伸びれば扉は窓の中で小さくなり、紙の下には潜らない。端末の背の高さにも依らない。

SP のカメラは**右斜め前・ほぼ水平**。正面からだと枠の奥行きも扉の隙間も写らず、
見下ろすと縦の線がすぼまって扉が傾いて見える。

### 書体

紙の文字は和文を先頭にする（ヒラギノ → Noto Sans JP）。アプリ共通の `CONTROL_FONT` は Inter が先頭で、
「Google でログイン」のように欧文と仮名が隣り合うと大きさと並びが揃わず崩れて見えた。
和文には字間を付けない（「ロ グ イ ン」とばらける）。

### その他

- 物は**扉・敷物・低い棚と一輪挿し**だけ。棚は「前室」であることを言う唯一の物で、線を足して部屋を説明しない
- 扉の名札は空けておく。名乗るのは紙のほう
- 言語の切り替えは右上の擦りガラスのピル 1 つ。**通り道（`/callback` `/auth/confirm`）では出さない**（`isPassage`）
- 動きを減らす設定では扉もカメラも動かさず、溶かすだけ
- WebGL が無いときは扉が出ないだけで、紙はそのまま使える

レイアウトに置くので、認証画面どうしを行き来しても扉（WebGL のコンテキスト）は作り直さない。

### フォームと扉の約束

フォームは扉の実体を知らない。`useEntrance()` の 3 つだけを使う。

- `compact` — 紙が狭いか（SP の 2 段を出すか）
- `setWaiting(true/false)` — 送信の前後
- `await enter()` — 認証が通ったあと、**行き先へ移る前**。溶け切ってから resolve する

扉の外（検証ハーネス・テスト）では `enter()` がすぐ解決するので、フォームは単体でも動く。

`useOauthCallback` / `useEmailConfirm` は読み込み直す直前に `beforeLeave(destination)` を待つ。
パスワード再設定（`/reset-password`）のように**扉の手前へ戻る**行き先では扉を開けない（`staysAtEntrance`）。

### 季節（七十二候）

一輪挿しに挿さる草花が、いまの候（七十二候）で替わる（`entrance/season.ts` と `scene.ts` の `drawSprig`）。

- **節気（15 日ごと・24 回）で花材そのものを替える。** 梅 → 猫柳 → 土筆 → 桜 → 山吹 → 藤 →
  青楓 → 菖蒲 → 蛍袋 → 笹 → 朝顔 → 蓮の葉 → 芒 → 桔梗 → 萩 → 彼岸花 → 実の枝 → 紅葉 →
  枯れ枝 → 山茶花 → 松 → 千両 → 蝋梅 → 椿
- **候（5 日ごと・72 回）では同じ花材の時間が進む。** 蕾が開き、丈が伸び、本数が増える
- 姿の型は線画で描き分けられる 7 つだけ（枝・草花・草・穂・松・大きな葉・つる）。
  葉・花・実・穂・針はその型に付く部品として描く
- 暦の表は持たない。日付 → 太陽黄経（近似式）→ 5° ごとの候、と導く（表は年ごとに作り直しが要る）

最初は葉の枚数だけを増減させていて「あまりにも地味」と差し戻された（PR #624 のレビュー）。
**一種を一輪挿しに投げ入れた姿**という見え方は、川瀬敏郎『一日一花』に倣っている — 整えず、
まっすぐ立てず、枯れ枝や実だけの枝も花材として扱い、余白を残す。

**変えるのは草花だけ。** 扉・棚・敷物・花器は季節で変えない。部屋の作りを動かし始めると、
置いてある物の必然性（世界観デザイン）と衝突する。飾りを増やすなら、その設計と合わせてから。
