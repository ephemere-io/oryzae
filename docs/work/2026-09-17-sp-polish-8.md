### R1. 中身を読み終えて戻すと、そのままシートが縮む

- 症状: シートの中でスクロールしているとき、中身を上まで読んで下へ戻すと、**内部のスクロールが尽きた瞬間に
  続けてシート自体が縮む**
- 希望: 内部が先頭まで戻りきったところで一度スクロールを終え、**もう一度下へ引いたときに初めて**シートが縮む
- 原因: シートの高さ（段）と中身のスクロールを**1 つのスクロール容器**で担っていた。シートは中身のぶんだけ高く、
  全画面より先はそのまま中身が流れる作りなので、戻すときも同じ指のまま段へ入っていった
- 直し方: **中身を別のスクロール容器にする**（`data-sheet-content`）。
  - シートの高さは容器と同じに固定し、中身の箱が残りを取る。容器のスクロールは段の切り替えだけを担う
  - 中身の箱は**いちばん高い段に着くまで `overflow-y: hidden`**。低い段では指はシートの高さに使う
    （Google マップと同じで、低い段から上へ払えばシートが上がる）
  - 中身が動き出したら `overscroll-behavior-y: contain`（この指ではシートへ渡さない）。**先頭に戻って指を離した
    ときだけ `auto` に戻す**ので、次の指で初めてシートが縮む。止めているのはブラウザの連鎖であって、スクロールを
    JS で数値で止めているわけではない
  - 中身の段（`content`）の吸着先は「見出し + 中身の高さ」。シートの高さを固定したぶん CSS だけでは分からないので、
    測って CSS 変数（`--oz-sheet-content`）で渡す。**吸着そのものはブラウザに任せる**

### R2. 問いを編集のシートは、いちばん小さい段からさらに引いたら閉じたい

- 直し方: モーダルのシート（`BottomSheet`）だけ、閉の位置を吸着先に戻す（`dismissible`）。いちばん低い段から
  さらに引くと閉じる（iOS のシートと同じ）。パレットや歯車で出し入れする板（発酵の結果・設定）は今まで通り、
  指では閉じない
- 吸着先の組は描いている間に変えない（WebKit が別の段へ吸着し直す）ので、閉の吸着先はシートの種類で固定する。
  配置の無い環境（テスト）では位置がいつも 0 なので、採寸できるときだけ「払いきった」と数える

## 追記: 瓶の問いの一覧でセミモーダルが出てこない（2026-09-17）

- 症状: 瓶の画面から問いの一覧を開き、アイテムを押しても「問いを編集」のセミモーダルが**見えない**
- 原因: 重なりの順。瓶の page は問いの一覧を本文（`main`）の中に `z-40` で重ね、殻のシートの席は `z-30`。
  同じ重なりの文脈に並ぶので、一覧のほうが上に来てシートを覆っていた。**`main` に付いていた `sp-rise` の
  アニメーションがたまたま重なりの文脈を作っていて**、そのあいだだけ症状が出なかった（動きを止める設定では必ず出る）
- 直し方: `main` に `isolation: isolate` を付けて、**本文の重なりをそこで閉じる**（画面が本文に重ねる層は、殻の
  ドック・シート・下端の列より上に来ない）。瓶の一覧の `z-40` も本文の中の値（`z-10`）に下げた
- 確かめた: 動きを止める設定（`prefers-reduced-motion: reduce`）で再現し、直したあとは Chromium・WebKit の両方で
  シートが一覧の上に出る。キーボードが出た想定で画面を縮めても出たまま。パレットの「問いの一覧」で開閉、上段の
  戻るで閉じる、シートのキャンセルで戻る、も通し

## 追記 2: 一覧から開いてもシートが出てこない（2026-09-17・実機）

- 症状（実機）: 瓶 → 問いの一覧 → アイテムを押しても**何も出てこない**。あわせて、一覧の上に地図の倍率の表示が
  出ていた（重なりを `z-10` に下げた私の直しの副作用。`z-40` に戻した）
- 追いかけた: ログイン無しで**実画面の `/jar`** を開ける手を使い（`page.route` で `auth/me` などだけ返す）、
  Chromium・WebKit の iPhone で一覧からアイテムを押した。どちらでもシートは出る（手元では再現しない）
- 疑い: 払いきりで閉じられるようにした（`dismissible`）とき、**閉の位置（容器の下）が吸着先に増えた**。開いた直後に
  段へ送るのが効かないと、シートは閉の位置に居る → 見張りが「払いきった」と読んで閉じてしまう。実機で「出てこない」
  のはこれで説明がつく（この直しを入れた版から症状が出ている）
- 直し方（保険）:
  - **閉じるのは指で払いきったときだけ。** 部品が段へ送った結果として閉の位置に居るなら、頼まれている段へ置き直す
    （`byFingerRef`。容器に指が触れたときだけ「指」と数える）
  - 段への送りは `scrollTo` ではなく `scrollTop` の直接代入にする（吸着やアニメーションの都合で効かないことがある）
- 確かめた: 実画面の `/jar`（Chromium・WebKit）で一覧 → アイテム → シートが出る。動きを止める設定でも、
  キーボードが出た想定で縮めても出たまま。指の受け渡し（中身を戻してもシートは縮まない／もう一度引くと縮む）と
  払いきりで閉じるのも通し

## 追記 3: 出てこない本当の理由（2026-09-17・実機のスクショで確定に近づく）

実機の「押す前／押した後」のスクショは**まったく同じ**（暗幕も出ない）。手元では、開発ビルドでも本番ビルドでも、
Chromium・WebKit の iPhone でも、**実画面の `/jar`** で再現しない（ログイン無しで実画面を開く手を使った）。

- 見立て: **払いきりで閉じられるようにした版から、閉の位置（`scrollTop` 0）が吸着先に増えた**。
  以前は 0 が吸着先ではなかったので、位置の指定が効かなくてもブラウザの吸着が勝手に段へ引き上げていた。
  いまは 0 のまま留まれるので、**開いたのに画面の外に居る**ことがあり得る。
  iOS は出る動き（`translate` の transition）の最中に `scrollTop` の指定を受け付けないことがある
- 直し方: 開いたあと、**出る動きのあいだ段へ置き直し続ける**（`ensureAtDetent`。指が触れていたら触らない）。
  動きが終わった時点（`transitionend`）でももう一度確かめる
- 確かめた: 「位置の指定が効かない」状況を作り（250ms のあいだ `scrollTop` を 0 に押し戻し続ける）、
  シートが消えずに段へ戻ることを Chromium・WebKit の両方で確認した。以前はここで閉じていた
- まだ実機では未確認。もし直っていなければ、`/verify/SpQuestions/edit-sheet` を実機で開いてもらえば、
  「部品そのものが出ないのか、瓶の重ね方の問題なのか」が切り分けられる

## 追記 4: 「押しても何も出ない」の仕組みを再現できた（2026-09-17）

実機の症状と同じ状態を手元で作れた。**中身の段の吸着先が、閉の位置と重なる**ことがある。

- 中身の段の印は「見出し + 中身の高さ」に置いてある（測って `--oz-sheet-content` で渡す）。
  この値が `0px` になると、印の位置は `min(0px, 100cqh) - 100cqh` ＝ **閉の位置とぴったり同じ**になる
- 問いの編集シートは中身の段から出る（`initialDetent="content"`）ので、開いた瞬間に閉の位置へ置かれる。
  暗幕の濃さも位置から決まるので暗幕も出ない。**押す前と押した後で画面が 1px も変わらない**
- 手元で `--oz-sheet-content: 0px` を強制したら、実機のスクショとまったく同じになった
  （`visibleHeight: 1` / 暗幕 `0.00`）。Chromium・WebKit の両方で再現
- なぜ実機だけ 0 になるのかは、まだ断定できていない（測る前の一瞬を見ているのか、実機の描画順か）。
  ただし **0 のときに閉の位置へ置かれるのが事故の本体**なので、そこを塞いだ

直し方（どちらも構造で塞ぐ。数値の力技ではない）:

1. **どの段も「見出しの行が見える」より低くならない。** 覗く段の印（＝見出しの行の高さ。測った中身の高さに
   依らない）を下限にする。中身の段がそれより低い＝測れていないので、**いちばん高い段に出す**
   （何も出ないくらいなら全部出す）
2. **測れないときは `--oz-sheet-content` を書かない。** 変数が無ければ既定の `100%` ＝ 面の上端 ＝
   いちばん高い段が使われる。さらに、測り直して値が変わったら**止まっている段へ置き直す**
   （測る前に置いた位置に取り残されない。指で触っている間は触らない）

確かめたこと（実画面の `/jar`、ログイン無しで開く手を使用）:

- 測れない状態（`0px` を強制）でも、シートは全画面で出て暗幕も出る（Chromium・WebKit）
- ふだんの状態は変わらない（中身の段・274px・暗幕 0.41）
- 指の動き: アイテムを押す → 中身の段 → 上に払う → 全画面 → 下に払う → 中身の段 →
  **もう一度下に払うと閉じる**（いちばん小さい段からの払いきり）

## 追記 7: 実機でまだ出ない。分かったことと、次に見るもの（2026-09-17）

実機のスクショ 2 枚（押す前・押した後）を**画素で比較したら差分ゼロ**だった。シートの面は
`overflow: hidden` で切られるので、閉の位置に居ても画素は変わらない。よって「出ていない」以上のことは
スクショからは分からない。

つぶした可能性:

- **古いビルドを見ていた** … 否。配信中の preview の JS に今回の計器の文字列があることを確認した
- **Service Worker が古い資産を貼り付けている** … 否。`public/sw.js` は navigate だけ介入する network 優先で、
  資産は一切キャッシュしない
- **押す場所が違う（鉛筆だけが押せる）** … 否。カード全体が `<button>`（`block w-full`）
- **配信中のビルドが壊れている** … 否。**preview の URL そのもの**を iPhone 相当（WebKit / Chromium、
  reduced motion も）で開くと、押した瞬間に中身の段で出る（`st=273` / 暗幕 0.41 / フォーカスも textarea）

直したもの（いずれも構造の穴。実機で直るかはまだ未確認）:

- **`pointerdown` を「指」と数えていた。** iOS は指を離したあと、**そのとき指の下にある要素へ合成の
  pointer/mouse イベントを送る**。一覧のアイテムを押して出したシートは、まさにその指の下に出てくるので、
  出た瞬間に「指で触られた」ことになり、段へ置き直す処理（`ensureAtDetent`）が丸ごと止まる。
  **touch は合成されない**ので、指の判定は `touchstart` だけにした
  - 一度「指が触れている間にスクロールが起きたときだけ指と数える」に変えたら、**払いきりで閉じる**が
    壊れた（スクロールの通知は指を離したあとに届くことがある）。`touchstart` で指、`touchend` で離した、
    の 2 つを別々に持つのが正しい
- 段の位置は**どれも閉の位置にはしない**（測れない印は 0 と見分けがつかないため）

次に見るもの: 計器（`sheet-probe`）を preview では自動で出すようにした。1 枚のスクショで
`mode=`（画面の状態が変わったか）・`sheets=`（描かれたか）・`st=`（どこに居るか）・`err=`（例外）が読める。

## 追記 8: 原因（実機の計器で確定）と、構造だけで直した形

実機の計器の読み:

```
mode=edit sheets=1 vv=717/0 inner=717
問いを編集 open d=content shown=true st=0 ch=717 sh=1434 top=717 h=717 cv=272px tr=none
```

- `mode=edit` … 押せている。`sheets=1` … シートも描かれている
- `shown=true` / `tr=none` … 出る動きも終わっている
- `cv=272px` … 中身の高さも正しく測れている
- **`st=0` / `top=717`** … 位置だけが 0（＝閉の位置）のまま。だから画面の外に居た

**原因: 閉の位置を吸着先（`scroll-snap-align: start`）にしていた。** iOS は出た瞬間にいちばん近い
吸着先＝閉の位置を選び、そこに留まる。`scrollTop` の指定はそのあと吸着に戻される。私はそれを
JS で押し込もうとして機械（`ensureAtDetent` の再指定ループ、指かどうかの判定、置き直しの保険）を
足し続けていた。**足す方向が逆だった。**

直した形（JS で位置を押し込まない。全部 CSS の吸着先の付け外しで表す）:

1. **閉の位置は既定では吸着先にしない。** 払いきりで閉じられるシートでは、**指が触れている間だけ**
   吸着先にする。「払いきって閉じられるのは指だけ」という規則が、そのまま構造になる
2. **出すときは行き先の段だけを吸着先にする。** 吸着先がひとつしか無ければ、ブラウザは必ずそこへ吸う。
   着いたら全部の段に戻す（そこから先は指で段を選べる）
3. 閉じる動きの間は吸着そのものを切る（閉じると決めたあとに段へ引き戻されない）
4. `ensureAtDetent`・指かどうかの判定（`byFingerRef` / `touchingRef`）・閉の位置からの引き戻しは全部捨てた

確かめ方（これが今回いちばん効いた）: **`scrollTop` の指定を丸ごと無効化**して（実機と同じ状況）、
ブラウザの吸着だけで正しく出るかを見る。`.tmp/scripts/r17-no-scrolltop.mjs`。

- 位置指定が一切効かない状態でも: `content` の段に出る（WebKit 273px / Chromium 274px・暗幕 0.41）
- 指の動きも同じ: 上に払う → 全画面 → 下に払う → 中身の段 → もう一度下に払うと閉じる
- ふだんの状態（位置指定が効く）も変わらない

## 追記 9: 出るようになったあとに残った 2 つ（実機 9:47〜9:51）

シートは出るようになった（計器: `st=273 top=444`）。残った指摘は 2 つ。

### 1. 一度タップすると「小さいバー」が上へスーッと移動する

**原因: 書く欄の `autoFocus`。** iOS はフォーカスした要素を見せようとして祖先を勝手に送る。シートの容器は
スクロール容器なので、出たばかりのシートごと上へ滑っていく（計器: `top=-87`）。

追記 6 で「もう跳ねない」と書いたのは誤り。中身を別のスクロール容器にしても、**容器そのものが送られる**。

`preventScroll` を付けて effect で当てると、今度は**キーボードが出ない**（iOS は指の操作と地続きでない
フォーカスでキーボードを出さない）。両立しないので、**フォーカスは当てない**。書く欄を押せばキーボードは出る。

### 2. 下から出てきたものの大きさを変えられない

**原因: 追記 8 で入れた「出すときは行き先の段だけを吸着先にする」の解除が効いていなかった。**
解除を「その段に止まったのを見てから」にしていたが、**ブラウザが配置のときに吸い付くとスクロールの通知が
来ない**ことがあり、そのときは解除されない＝吸着先がひとつのままで段を変えられない。

直し方: 止まったかどうかを待たない。

- **指が触れたら解く**（これから段を選ぶのだから、全部の段が吸着先でよい）
- **出る動きが終わったら解く**（`transitionend` と `getAnimations().finished` の両方。動きが無い環境でも解く）

### 確かめ方（実機の 2 つの条件を作る）

`.tmp/scripts/r18-resize.mjs` — (1) `scrollTop` の指定を効かなくし、(2) **指が触れるまでシートの容器の
`scroll` の通知を届かせない**。この状態で:

- 開いた時点で吸着先が 2 つ（＝段を変えられる）・`content` の段・274px
- 上に払う → 全画面 → 下に払う → 中身の段 → もう一度下に払うと閉じる

## 追記 10: 段階的に小さくならず、一気に消える（2026-09-20）

オーナー: 「下に下げようとすると一気に表示が消える。上に上げてサイズ変更、下に下げて非表示、という
**段階的な**サイズ調整がしたい。エントリーのセミモーダルと同じ部品なら、できるはず」。

同じ部品だが、**渡していた段の数が違った**。

| | 段 |
| --- | --- |
| エントリーの「発酵の結果」 | 覗く / 半分 / 全画面（3 つ） |
| 問いを編集（直す前） | 中身 / 全画面（2 つ） |

中身がいちばん低い段なので、そこから下に払う＝**いきなり閉じる**。段を下げる余地が無かった。

直したこと:

1. **段を 3 つにする**（覗く / 中身 / 全画面）。中身の段を最小にしない
2. **閉の位置が吸着先になるのは、いちばん低い段に居るときに指が触れたときだけ。**
   どこからでも吸着先にすると、高い段から大きく払っただけで途中の段を飛ばして閉じる

## 追記 13: 根本原因 — 底を吸着先にした瞬間に iOS はそこへ飛ぶ（2026-09-22）

オーナー: 「また同じ問題。いちばん小さいサイズで上に上げようとすると、セミモーダルごと消える。

計器: 触る前 `open st=273` → 上に上げようとした直後 `closing st=0`。**上に動かしたのに位置は底（0）。**
指の向きと逆なので、指の動きで行ったのではなく、**触れた瞬間に底へ飛んでいる**。

iOS の WebKit は、指が触れている最中に吸着先（scroll-snap-align）の一覧が変わると、吸着の状態を作り直して
**DOM 順で最初の吸着先へ飛ぶ**。最初の吸着先は底の空き。これで全部つじつまが合う:

| 版 | 底を吸着先にしたタイミング | 実機の症状 |

| 追記 12（最小の段だけ） | 触れた瞬間 | 「上に上げようとすると消える」 |
| 追記 11（仕掛けなし） | **一度もしない** | **「素晴らしい、狙い通り」** |

**結論: 底は一瞬たりとも吸着先にしない。** 追記 12 で「見出しだけの段との組み合わせが原因」としたのは誤り。
底を吸着先にすること自体が原因だった。

### 「引っ張って閉じる」の作り方（底を吸着先にせずに）

吸着は指を離した瞬間にしか働かないので、**触れている間はシートは指について底まで自由に下がる**。だから閉じる
判定は離した瞬間の位置だけで足りる。追記 11 の「底まで引き切る」は、いちばん低い段の見出しが画面の下端から
段の高さぶん上にあるため、実機では指が先に画面の外へ出た。代わりに、ブラウザが吸着先を選ぶときの
**「近い方」の規則**をそのまま使う:

- **離した位置が、いちばん低い段より底に近ければ閉じる。** 段のほうが近ければブラウザが段へ戻す
- 数値のしきい値は持たない（段の位置と底の中点はブラウザの「近い方」と同じ）
- 弾いても閉じない（離した位置で見るため）。引けば必ず閉じる。オーナーの言葉は一貫して「引っ張る」

## 追記 15: いちばん低い段より下を、スクロール範囲から無くす（2026-09-22）

オーナー: 「いちばん小さいセミモーダルのとき下に引っ張ると、引っ張れるのに閉じられない。引っ張れるということは
何かアクションができるアフォーダンスを与えている。どう思うか」。

正しい。空きが「容器いっぱい」だったので、いちばん低い段の下に「閉の位置」がスクロール範囲として残り、
指がそこまで **1:1 で 273px** 引き下ろせた（計器 `st=86`）。離せば戻る＝偽の手がかり。iOS の「端で少し抵抗して
戻る」は限界の合図だが、273px ついてくるのは「続ければ閉じる」と約束しているのと同じ。

### 直し方: 空きの高さを「容器 − いちばん低い段」にする

- スクロール位置 0 ＝ いちばん低い段。それより下は物理的に無い（OS 標準の端の小さな跳ねだけが残る）
- **閉の位置がスクロール空間に存在しなくなる。** iOS が 0 に飛ぼうが、そこが正しい置き場所。今日までの不具合の
  種そのものが消えた
- 出す／消す動きはスクロールではなく容器ごとの平行移動（translate）なので、空きの高さに依らない
- 空きの高さは CSS の式（`spaceAbove(detents[0])`）: 覗く＝`100cqh − 見出し`、中身＝`100cqh − min(中身, 100cqh)`、
  半分＝`50cqh`、全画面＝`0`。測った高さは容器の CSS 変数（`--oz-sheet-header` / `--oz-sheet-content`）から継ぐ。
  `detents` は低い順に並べる約束（`DockSheet` も `detents[0]` を最低の段として扱う）

### 途中で踏んだ 2 つ（どちらも構造で塞いだ）

1. **スクロールアンカリング**: 測定で空きが 0 → 391px に伸びたとき、ブラウザが「見えていたシート」を同じ場所に
   留めようと位置を動かし、出た瞬間に全画面になった → 容器に `overflow-anchor: none`（位置は段が決める）
2. **吸着の追従（re-snap）**: 測る前は空きが 0 で、中身の印と全画面の面が同じ位置 0 に重なる。吸着が効いていると
   ブラウザは全画面の面を吸着相手として覚え、空きが伸びたときに相手を追いかけて全画面まで動く（仕様どおり）。
   通常条件では JS の代入が上書きするので隠れていたが、代入が効かない環境（実機の再現）で出た
   → **段の位置が決まるまで吸着を入れない**（`measured` になってから `scroll-snap-type`）。測定は layout effect

## 追記 24: 試作の実機 2 回目 — 読み終えても縮まない／本文に入力できない（2026-09-23）

オーナー: 「本文のスクロールは全部終わったのにセミモーダルのサイズを変えられない」「そもそも入力できない」
「十分にテストやってから報告してる？」。後者は正当で、私の検証は Chromium の touch で板の動きだけを見ており、
本文に入力できるかと、iOS でしか起きる経路（キーボードでビジュアルビューポートが縮む・上端の跳ね返り）を
試していなかった。道具の限界を言い訳にせず、Vaul の中身（`dist/index.mjs`）を読んで原因を特定した。

### 入力できない — Vaul の `isInput` は contentEditable も数える

- iOS は中身が上端にあるとき下へ引くと、ネイティブの跳ね返り（overscroll）が指を奪って `pointercancel` になり、
  Vaul の drag に届かない → 中身の箱に `overscroll-behavior: none`（跳ね返りを切れば指は板へ届く）
- Vaul の判定は `element.scrollTop !== 0`（厳密）。iOS は減速の末に 0.3px などの端数で止まることがある →
  触れた瞬間に端数（0 < scrollTop < 1）を 0 へ揃える

## 追記 25: 板が「モーダル」だった — 発酵の結果が出ていると本文が書けない（2026-09-23）

オーナー: 「発酵の結果が表示されてる時に本文が書けない。セミモーダルの挙動はある程度良い。構造的に解決して」。

### 再現できた

`.tmp/scripts/r34-vaul-body-focus.mjs`（WebKit の iPhone 相当）で、iOS のキーボードを
**フォーカスに反応してビジュアルビューポートが 300px に縮む**ところまで作り、問いを結んで板を出してから
本文を押した。結果:

- 本文に `focusin` が入った**同じミリ秒**に `focusout`、続けて板に `focusin`
- 以後 2 秒間ずっと焦点は板。打った文字は本文に入らない
- 焦点を戻しているのは Radix の `FocusScope`（`handleFocusIn` → `focus(lastFocusedElement)`）
- ついでに `<main>` が `aria-hidden="true"` になっていた（本文が支援技術から消えている）

### 原因: Vaul の `modal={false}` は Radix に届かない

`vaul/dist/index.mjs` の `Root` は `DialogPrimitive.Root` に `defaultOpen` / `onOpenChange` / `open` しか
渡していない。**`modal` を渡していない**。Radix の既定は `modal: true` なので、Vaul 側で `modal={false}` と
書いても、Radix から見た面は常にモーダルの `DialogContentModal` になる。これが付けるのは 3 つ:

1. 焦点の檻（`FocusScope` の `trapped: context.open`）— 面の外に焦点が移ると引き戻す
2. `hideOthers(content)` — 面以外を `aria-hidden="true"`
3. `disableOutsidePointerEvents` — `body` の `pointer-events` を止める（Vaul が rAF で戻している）

Vaul の `modal` prop が効くのは Vaul 自身の暗幕と body の後始末だけ。**板（本文の隣で読むもの）には
3 つとも誤り**で、1 が「本文が書けない」の正体。prop では外せない（`trapFocus` は `...props` の**後**に
書かれていて上書きできない）。1.1.2 が最新なので上流の修正待ちもできない。

### 直し方: Vaul の中に非モーダルの Dialog の文脈を置く

Radix の `Content` は**いちばん近い** Dialog の文脈を読む。そこで Vaul の `Drawer.Root` の中、
`Drawer.Portal` の外側に `<Dialog.Root modal={false} open={open}>` を挟む。面は `DialogContentNonModal`
になり、檻も `aria-hidden` も `pointer-events` の停止も付かない。

前提は「Vaul と client が**同じ実体**の `@radix-ui/react-dialog` を読む」こと。別実体だと React の文脈が
別物になり、この上書きは**黙って**効かなくなる（型もテストも通ってしまう）。そこで
`apps/client` の依存に Vaul が解決するのと同じ版（`1.1.23`）を直接足し、
`test/architecture/vaul-dialog-is-shared.test.ts` で解決先のファイルの同一性を見張る。

### 分かったこと（全面移行の判断材料）

**Vaul は「モーダルのシート」には良いが、「非モーダルの板」はそのままでは作れない。**
設定・問いの選び手・写真のような**モーダル**は Vaul にそのまま載せられる。本文の隣に出す板だけは
この一枚の上書きが要る。

### 実機の 4 つは、それぞれ別の原因だった

- **ちょっと触ると一気に段が飛ぶ** — 見出しの行の `onClick` が「いちばん低い段へ」を呼んでいた。
  指が動いても `click` は出るので、少し引いただけで全画面 → 覗くへ飛ぶ。**指が 8px 以上動いたら押したと見なさない**、
  押したときも**1 段だけ**動かす（払いは Vaul の drag に任せる）
- **全画面なのに中身が送れないことがある** — Vaul は面に `touch-action: none` を当てる（自前の drag のため）。
  内側の箱にも効くので、ブラウザが指で送れない。内側に `touch-action: pan-y` を戻す。

## 追記 27: 動かすのはブラウザ、JS は 2 回だけ決める（2026-09-23）

オーナー: 「最大サイズになった後、すぐに内側のスクロールを開始することが出来ません。なんか JS で毎回計算が
走ってる感じがする。もっと即レスポンスがある世界になってほしいし、CSS でうまくやった方がヌルヌルと、
操作量と操作タイミングに応じたパフォーマンスが作れそう。ライブラリ導入してもそこまで抜本的に変わってない」。

**そのとおりだった。** 原因は 2 つの engine それぞれにあり、どちらも「JS が止まるのを待ってから切り替える」形だった。

### CSS の吸着（既定）— 止まった段を見てから中身を開けていた

`sheet.tsx` は「2 フレーム続けて同じ位置」かつ「その位置がどれかの段と一致」を見てから、中身の箱の
`overflow-y` を `auto` にしていた。つまり**指を離して、慣性が止まって、段に一致して、はじめて読める**。
段に着いたかどうかはスクロール位置だけで分かるので、スクロールの通知のたびに比較 1 回で当てる
（値が変わったときだけ書く。毎フレーム同じ値を書くと様式が無効になって粘る）。

内側から外側へ渡すか（読み終えた指で縮ませない）も、毎フレーム見張って `overscroll-behavior` を
書き換えていた。これも**指を置いた瞬間に 1 回**決めれば足りる（`canDragSheet`）。見張りの rAF を 2 つとも捨てた。

残った JS は次の 2 つだけ:

- スクロールの通知ごとに `scrollTop` の比較 1 回（中身を開けるか）
- 指を置いた瞬間に `scrollTop` の比較 1 回（この指で板を動かしてよいか）

動き（慣性・吸着・弾み）はすべてブラウザのスクローラが持つ。指の量とタイミングにそのまま乗る。

### Vaul（`?sheet=vaul`）— 動きを JS が持っている限り同じことが起きる

Vaul は pointermove ごとに `transform` を書き、離すと **0.5 秒の CSS transition を自分で持つ**。
この 0.5 秒の間に触ると、`shouldDrag` が「まだ段の途中（`getTranslate` が 0 でない）」と読んで
**その指を板に渡す**。指が離れるまで中身は送れない。オーナーの「最大になった後すぐに送れない」はこれ。

ライブラリを入れても「動きを JS が持つ」構造は変わらない。**推す形は CSS の吸着**（既定の URL）。
Vaul は比較用に `?sheet=vaul` で残してある。

## 追記 28: 待っていたのは「着くまで」だった — 吸着の終わりは長い（2026-09-23）

オーナー: 「まだ、セミモーダルが画面いっぱいになった後、0.5 秒くらい立たないと内側のスクロールができない。
最大サイズになって、かつ外側のスクロールが止まった時、という判定を JS でやってるから触り心地が悪いのでは」。

半分あたっていた。**「止まった」はもう見ていない**（追記 27 で外した）。残っていたのは
「**着いた**（残り 1px 未満）」で、これが遅かった。

### 実測（Chromium・半分から払って全画面へ、16ms ごと）

```
  8ms 高さ276  残り274  hidden
141ms 高さ455  残り 95  hidden
158ms 高さ515  残り 35  hidden   ← 見た目はもう全画面
258ms 高さ534  残り 16  hidden
357ms 高さ545  残り  5  hidden
408ms 高さ549  残り  1  auto     ← やっと開く
```

**吸着の動きは終わりが長い。** 残り 35px から 0px までに 250ms かかる。指はとっくに離れているのに、
最後の 1px を待っていた。オーナーの「0.5 秒」はこれ。

### 直し: 「着いたか」ではなく「決まったか」を見る

いちばん高い段とその 1 つ下の**中点**を越えたら開ける。これはブラウザが吸着先を選ぶのと同じ問いなので、
中点を越えた時点で「全画面に決まった」と言い切れる。指はまだ外側の容器に latch されているから、
先に開けておいても内側が動き出すことはない。比較の回数は 1 回のまま（上の表なら 141ms で開く）。

### ついでに: 止まりの検出を `scrollend` に渡す

止まった段を知るための「2 フレーム続けて同じ位置」の rAF を、`scrollend`（Safari 18.2+ / Chrome 114+）が
あるときは使わない。暗幕を持たない板では、**スクロール中に走る JS が無くなる**（比較 1 回だけ）。
無いブラウザでは今までどおり rAF で代用する。

## 追記 29: 動いているスクローラは次の指を取る（WebKit の latch）（2026-09-23）

オーナー: 「最大幅になった後にすぐにもう一回同じ方向に指でスクロールした時に、すぐに内側のスクロールが
出来るようにしたい」。追記 28 で中身は 117ms で開くようになったのに、まだ動かない。

### 測ったら Chromium では再現しなかった

払って全画面にしてから 60 / 150 / 300 / 600 / 1200ms 後に、もう一度上へ引く
（`.tmp/scripts/`（scratchpad）の r38）。**どの待ち時間でも中身は送れた**（scrollTop 388〜426）。
つまりこれは Chromium には無い挙動＝WebKit（iOS）の作法。

### 原因: 慣性の残っている容器が、次の指を取る

WebKit の overflow スクロールは UIScrollView に写される。**減速中の容器に触れると、その指はその容器の
ものになる**（減速を止めた指がそのまま同じ容器の続きになる）。吸着の尾は 250ms 以上あるので、
全画面に着いた直後の 2 本目の指は**外側**に取られ、外側はもう上へ動けないので何も起きない。
「0.5 秒待たないと内側が動かない」の正体。

### 直し: 触れた瞬間に、動きを終わらせて持ち主を 1 つに決める

`takeGesture`（touchstart / pointerdown の捕捉段階）で 2 つだけやる。

1. **いちばん近い段の位置へそのまま置く** — 慣性と吸着の尾をここで終わらせる。位置は吸着先そのものなので
   跳ねないし、置き直しも起きない。「触れたら止まる」という当たり前の手触りでもある
2. **外側の `overflow-y` でこの指の持ち主を言い切る**（`canDragSheet`）— 読んでいる途中の指のあいだ、
   外側は `hidden` ＝ **そもそもスクローラではない**ので取りようが無い。指が離れたら戻す

これで内側の `overscroll-behavior` の切り替えは要らなくなった（外側が動けないなら渡しようが無い）。
段の規則（`sheet-gesture.ts` の表）はそのままで、伝え方がブラウザにとってより直接的になった。

実機で確かめる必要があるのは 2 本目の指だけ（Chromium では元から通っていた）。

## 追記 35: 中身から板への受け渡し（決まりは指が触れる**前**に置く）（2026-09-23）

オーナー: 「最大表示の状態で、指を上から下にスワイプしたとき、外側のサイズを変更してほしい。
基本原則としては、外側のレイヤーですべてのスクロールが終わった後に内側のスクロールに入る仕様」
「それを要求すること自体に無理があるのであれば教えてください」。

**無理ではない。** ネイティブと同じ「受け渡し（scroll chaining）」で出る。追記 33 で
`overscroll-behavior: contain` を常時にしていたので渡らなくなっていた。

### 決まりは**スクロールが終わった時点**で置く

中身の箱の `overscroll-behavior` を、止まった位置で決める:

- 上端で止まっている → `auto`（次の指で下へ引けば板が縮む）
- 途中で止まっている（読んでいる） → `contain`（上端に着いてもそこで止まる）

**触れた瞬間に書いてはいけない。** 実測で、触れた瞬間に `auto` にしても板へ渡らなかった。
ブラウザは指が触れた瞬間に「この指をどこへ渡すか」を決めるので、決まりは**その前**に置いておく必要がある。
終わった時点で書けば、次の指はいつも正しい決まりの上で始まる（`scrollend`、無ければ 2 フレームの見張り）。

これでオーナーの言う段階がそのまま出る:

1. 全画面で中身を読む（板は動かない）
2. 上端まで戻す。**そこで止まる**（勢いで畳まれない）
3. 離してもう一度引く → **板が縮む**

### 切り分けの記録

「渡らない」を追いかけて、素のページで入れ子のスクロール容器を作り、吸着・`container-type`・
`pointer-events: none`・`oz-sheet-pass`・面の高さを 1 つずつ変えて試した（`scratchpad/chain.mjs`、
`r44-bisect.mjs`）。**どれも原因ではなく**、アプリでも指で操作すれば渡っていた。
渡らなかったのは**検証スクリプトが中身の位置を JS で 0 に戻していたから**で、
指だけで同じ道筋をなぞると渡る（`r39` の 10 番を指だけの手順に書き直した）。

全画面まで行くシートはこれまでどおり容器と同じ高さ（中身がはみ出しても伸びない）。

### 直したこと 2: いちばん高い段の判定に 1px の遊び

「いちばん高い段に決まったか」は `scrollTop >= 中点` で見ていた。段が 1 つだけのシートは
スクロールできる幅が 0 なので、印が小数で 0.3px 上に出ているだけで**永久に決まらない**
＝中身が開かない（実測: 行の操作のシートで `overflow: hidden` のまま）。
このファイルの他の判定と同じく **1px 未満は同じ位置**として扱う。

### 直したこと 3: モーダルのシートの下の余白にホームバーぶんを足す

`viewport-fit=cover`（`app/layout.tsx`）なので画面はホームバーの下まで広がる。`BottomSheet` の
下の余白は `pb-8`（32px）固定で、**最後のボタン（保存・削除）がバーに重なっていた**。
`calc(2rem + env(safe-area-inset-bottom, 0px))` にした。下端に出る他の部品（`action-palette.tsx`・
`sp-confirm-sheet.tsx`・`sp-photo-import-sheet.tsx`）は元から同じ扱い。

### 直したこと 4: 全画面に着いた直後の待ちを短く

容器の `overscroll-behavior` を `contain` から **`none`** に。段の外へ弾まなくなるので、
払って全画面に着いたあと「弾んで戻る」ぶんの待ちが消える（オーナー: 「最大幅になった直後にすぐ
下から上になぞるとスクロールできない」）。iOS の指の取り合い（減速中の容器が次の指を取る）は
残るので、**完全には消えない**。
