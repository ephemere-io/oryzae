## 今回の指摘（原文の要旨）

1. 最初に開いた時に全部 0 件と出る
2. 全体的にスマホの体験としてローディングとアニメーションを。タップして 0.x 秒で何か返らないと安っぽい。
   タップしたときの体験を徹底的に。世界中の文献・記事のベストプラクティスに当たること
3. エントリー画面だけ、パレットから消せるのはどうか（よく考える）
4. 「瓶に納めて発酵させる」が長い
5. 発酵の結果: セミモーダルの大きさが変えられない・中身が見えない。パレットで出し入れしたい。
   **発酵の結果を見ながら書くとは何か、スマホではどういう体験であるべきか**を深く考えて実装
6. 写真: パレットから貼っても文中に入らず、画面下にプレビューが出るだけ。どうあるべきかを考えて実装
7. インターネットが無いときに端末に保存できるように
8. 設定シートを開いた状態で画面中央を押して下へ動かすとブラウザが再読み込みする。シートは中身に
   合わせて小さく。開いている間に再読み込みが起きないように（Google マップのセミモーダルを観察せよ）

## 調べたこと（ベストプラクティスの要点と出典）

- **押した印は 100ms 以内。** Apple HIG・Material とも「タップから 100ms 以内に見た目が変わる」を
  基準にする。指は hover を持たないので「押している／いない」の 2 状態を必ず作る。
  iOS Safari は `touchstart` の listener が 1 つでも無いと `:active` を出さない
  （出典: [iViewTouch](https://iviewtouch.com/2025/11/touch-ui-design-7-best-practices-that/)、
  [UXPin](https://www.uxpin.com/studio/blog/responsive-design-touch-devices-key-considerations/)）
- **動きの長さ。** 微細な応答（押した印）は 100ms 前後、画面内の遷移は 200〜300ms、モーダルや画面の
  入れ替わりは 300〜400ms。入ってくるものは ease-out、出ていくものは ease-in。500ms を超えると鈍い
  （出典: [Material motion](https://m1.material.io/motion/duration-easing.html)、
  [NN/g](https://www.nngroup.com/articles/animation-duration/)）
- **待ちは「何が来るか」を先に置く（骨組み）。** 骨組みはスピナーより体感で 30〜50% 速い。
  0〜300ms は何も出さず、それ以上なら骨組み。処理（送信）の待ちはスピナーでよい
  （出典: [LogRocket](https://blog.logrocket.com/ux-design/skeleton-loading-screen-design/)、
  [onething](https://www.onething.design/post/skeleton-screens-vs-loading-spinners)）。
  本アプリでは `useDelayedTrue`（150ms）+ `Skeleton` が既にこの作法（§66）
- **Google マップのシート。** 非モーダル（地図は触れる）・3 段（覗く／半分／全画面）・つまみでも
  中身でも引ける・低い段では 1 行の要約、半分で要点、全画面で全部・低い段から下へ引いても閉じない
  （出典: [Mobbin](https://mobbin.com/glossary/bottom-sheet)、
  [BottomSheetBehavior](https://developer.android.com/reference/com/google/android/material/bottomsheet/BottomSheetBehavior)）
- **引っ張り更新の抑止。** `overscroll-behavior: none` は Chrome では `body`、**Safari では `html`**
  に付けないと効かない。両方に付ける。スクロールしない要素に `touch-action: pan-y` を付けると、
  指の動きが親（文書）へ連鎖して Safari の更新が走る
  （出典: [Matuzović](https://www.matuzo.at/blog/2022/100daysof-day53)、
  [ebidel/demos#6](https://github.com/ebidel/demos/issues/6)）
- **オフライン。** 書き込みを端末の「送信箱」に置き、`online` で順に流す。再送は冪等（同じ id への
  PUT）。iOS は Background Sync を持たないので、ページ側で流す
  （出典: [amux outbox](https://amux.io/guides/pwa-offline-sync-outbox-pattern/)、
  [LogRocket offline-first](https://blog.logrocket.com/offline-first-frontend-apps-2025-indexeddb-sqlite/)）
- **本文の中の写真（モバイル）。** 1 つの入力欄に画像は置けない。実運用のアプリは本文を
  「文のブロックと写真のブロックの列」として持つ（Notion のモバイルも同じ）
  （出典: [DEV](https://dev.to/thomasnowheredev/notion-style-block-editor-for-any-framework-fk6)）

## F. 全体（体験の土台）

### F1. 最初に開くと全部 0 件

- [x] 症状: 書斎を初めて開くと、ピルが「JAR 0つの問い・ENTRIES 0件・ARCHIVE 0冊・BOARD 0枚」。
- 原因: `useStudyState` は取得中も `live`（空）を返す。前回の絵（`readStaleCache`）があれば数は前回の値に
  なるが、**初回と失敗時**は 0 が数として出る。0 は「無い」という意味を持つので、待ちの間に出してはいけない。
- 直し方: hook が **`countsKnown`**（`(!loading && !failed) || cached !== null`）を返す。`StudyLabels` は
  `counting`（数が未確定）を受け、数の代わりに小さな骨組み（幅 2 文字の淡い枠）を出す。語（JAR 等）は出す。
- 場所: `features/shared/study/hooks/use-study-state.ts`、`components/study-labels.tsx`（+verify）、
  `components/study-home.tsx`。
- 完了条件: 取得中のピルに数字が無い。取得後に数が入る。verify の `counting` fixture。

### F2. タップの応答と画面の動き

- [x] 症状: 押しても何も変わらない要素がある（ピル・一覧の行・問いの円・チップ）。押した印の速さが
  まちまちで、応答が返るまで「効いたのか」分からない。
- 原因: 押した印を部品ごとに `active:scale-95` で足していて、足していない部品が残る。iOS Safari は
  `touchstart` の listener が無いと `:active` を出さない。
- 直し方:
  - `globals.css` に **指の端末だけ**（`@media (hover: none)`）の共通の押した印: `button:active`、
    `a:active`、`[role=button]:active` に `transform: scale(0.97)` と `--hover-wash` の地、
    `transition: 80ms`。`-webkit-tap-highlight-color: transparent`（灰色の四角を消し、自前の印にする）。
    `data-no-press` で個別に外せる（円のドラッグ中など）
  - `SpShell` が `touchstart` の空 listener を 1 つ張る（iOS の `:active` を起こす）
  - 画面の入れ替わり: `SpShell` の本文を `pathname` で鍵にして 220ms の `sp-rise`（既存の keyframes）。
    reduce 設定では無効
  - 押してから画面が来るまで: 書斎のピルは押した瞬間に濃くなり（`aria-busy`）、行き先の `loading.tsx`
    が骨組みを出す（既存）。瓶の円は押した瞬間に 1.04 倍（既存のドラッグ時の見た目を押下にも）
- 場所: `app/globals.css`、`features/sp/navigation/components/sp-shell.tsx`、`study-labels.tsx`。
- 完了条件: 指で押せるものすべてに 100ms 以内の印。`/verify` の各部品で `:active` の style を確認。

### F3. 読み込みの作法を全画面に

- [x] 症状: 画面によって待ち方が違う（骨組み・何も出ない・0）。
- 直し方: §66 の作法（150ms 猶予 + 骨組み）を点検し、無い画面に足す。今回対象: 書斎（F1）、エントリーの
  発酵の結果（G3: 取得中は覗き段に骨組み）、写真（G4: 貼った瞬間に仮の枠、上がったら実物）。
  瓶・ボード・一覧は既に骨組みがある。
- 完了条件: 全画面で「押した → 100ms で印 → 300ms 以内に骨組みか実物」。

### F4. オフラインでも端末に残す

- [x] 症状: 電波が無いと自動保存が失敗し、書いたものが端末にも残らない（新規の下書きだけ localStorage
  に退避していた。既存の編集は何も残らない）。
- 原因: `useAutosaveEntry` は失敗すると「次の入力まで待つ」。オフラインを知らず、復帰しても再送しない。
- 直し方:
  - `lib/use-online-status.ts`: `navigator.onLine` + `online`/`offline`
  - `useAutosaveEntry`: 失敗したら **10s → 30s → 60s** で再送、`online` で即再送。`{ pending, offline }` を返す
  - **端末の写し `useEntryLocalCopy(entryId)`**（shared）: 入力のたび（300ms）に localStorage へ
    `{ content, mediaUrls, updatedAt }`。サーバーが同じ内容を保存できたら消す。開いたとき、写しがサーバーの
    内容より新しく中身が違えば写しを採用して「編集中」にする（＝電波が戻る前に閉じても、次に開けば続きから）
  - 上段の状態: オフラインで未保存なら「オフライン・この端末に保存」。復帰して保存できたら「保存しました」
- 場所: `lib/use-online-status.ts`（+test）、`features/shared/entries/hooks/use-autosave-entry.ts`（+test）、
  `features/shared/entries/hooks/use-entry-local-copy.ts`（+test）、`sp-entry-editor.tsx`、i18n 4 locale。
- 完了条件: 機内モードで書く → 上段が「オフライン・この端末に保存」→ 閉じて開き直しても残っている →
  機内モードを切ると「保存しました」に変わる。

### F5. シートを開いている間の引っ張り更新、シートの高さ

- [x] 症状: 設定シートの中央を押して下へ動かすと Safari が再読み込みする。シートが中身より大きい。
- 原因: (1) `overscroll-behavior: none` を `body` にしか付けていない（Safari は `html`）。(2) シートの中身に
  `touch-action: pan-y` を付けているが、中身がスクロールしない高さのときは指の動きが文書へ連鎖する。
  (3) 段（detent）が 45% / 92% の固定で、中身の高さを見ていない。
- 直し方: `html, body { overscroll-behavior: none }`。`BottomSheet` の中身は **スクロールできるときだけ
  `pan-y`**、できないときは `none`（ResizeObserver で判定）。段に **`'content'`（中身の高さ）** を足し、
  設定シートは `detents={['content']}`（それ以上には上がらない、下へ引けば閉じる）。
- 場所: `app/globals.css`、`components/ui/bottom-sheet.tsx`（+verify）、`sp-editor-settings-sheet.tsx`。
- 完了条件: 実機で、シートの中身のどこを押して下へ動かしてもシートが下がり、再読み込みが起きない。

## G. エントリー

### G1. 削除をパレットから外す

- [x] 指摘: 「エントリー画面だけ、パレットから消せるようにさせちゃうのはどうなんでしょうか」。
- 考え: パレットは**書いている最中に何度も押す手**（写真・漬け込む）の席。削除は稀で取り返しがつかない。
  同じ列に並べると、指の癖で押す（確認シートがあっても「押してしまった」体験が残る）。Notion のモバイルは
  削除を右上の「…」の中に置き、iOS の設定画面は破壊的な操作をシートの末尾に赤字で離して置く。
  この画面の右上は既に「この画面の設定」なので、**設定シートの末尾に「このエントリーを削除」**を離して置く
  （既存エントリのときだけ）。パレットは写真・漬け込むの 2 つに。
- 場所: `sp-entry-editor.tsx`、`sp-editor-settings-sheet.tsx`（+verify）、i18n。
- 完了条件: パレットに削除が無い。設定シートの末尾から削除 → 確認 → 書斎へ。

### G2. 「瓶に納めて発酵させる」が長い

- [x] 直し方: PC と同じ語 **「漬け込む」**（`editor.pickle`）。漬けた後は「発酵中」。上段の状態は
  「発酵を始めました ✓」のまま。4 locale。
- 場所: i18n `sp.editor.ferment_title` / 新 `ferment_done_short`、`sp-entry-editor.tsx`、test。

### G3. 発酵の結果を見ながら書く

- [x] 指摘: 大きさが変えられない・中身が見えない・パレットで出し入れしたい。「見ながら書く」とは何か。
- 考え（設計）:
  - PC では手紙・言葉・抜粋が本文の**横**に居て、目だけが行き来する。手はキーボードから離れない。
    「見ながら書く」＝**読む → 少し書く → また読む**の往復を、手も視線も大きく動かさずに続けられること。
  - スマホには横が無い。往復は**上下**で作る: 本文の下に**非モーダルのドック**（Google マップのシート）を
    置き、3 つの高さを持つ。
    - **覗く**（56px）: 問いと、いま見ている言葉 1 つ。書いている間はこれ。キーボードが出ている間はここに固定
    - **半分**（殻の 45%）: 手紙の冒頭 3 行・言葉の chips・抜粋 3 件。本文の上半分は見えたまま
    - **全画面**（殻の 88%）: 手紙の全文と抜粋の全文
  - **モーダルにしない**: 背景の暗転なし、本文は触れる。ドックの高さぶん本文の下に余白を足し、書いている行が
    隠れない。本文を押してキーボードが出たら覗く段へ縮む（読む→書くの切り替えが 1 タップ）。
    覗く段を押せば本文からフォーカスを外して半分へ（書く→読む）
  - **パレットの「発酵の結果」で出し入れ**（結んだ問いに完了した発酵があるときだけ並ぶ。出ている間は印）。
    下へ引き切っても消えない（覗く段で止まる）。消すのはパレット
  - 取得中は覗く段に骨組み（F3）
- 場所: `lib/sp-chrome-context.tsx`（`dockSlot`、`dockHeight` → 殻が本文の `paddingBottom` に）、
  `features/sp/navigation/components/sp-shell.tsx`、新 `components/ui/dock-sheet.tsx`（非モーダル・段・
  ドラッグ。`BottomSheet` の作法を共有）（+verify）、`sp-fermentation-drawer.tsx` → `sp-fermentation-dock.tsx`
  （+verify +test）、`components/ui/palette-icons.tsx`（結果の印）、i18n。
- 完了条件: パレットで出し入れ、3 段をつまみでも中身でも行き来、本文を押すと覗く段に縮む、
  覗く段を押すと半分に戻る、引っ張り更新が起きない。

### G4. 写真を本文の中に

- [x] 指摘: パレットから貼っても文中に入らず、下にプレビューが出るだけ。
- 考え（設計）:
  - PC は既に本文の中に写真を置ける（U+FFFC のプレースホルダ + `effects.inlineImages[{offset, storagePath,
    …}]`、`docs/entry-photo-guide.md`）。**保存形式は PC と同じにする**（変えるべきでないもの）。
  - SP の本文は textarea で画像を描けない。本文を **U+FFFC で切った「文のブロックと写真のブロックの列」**
    として描く（Notion のモバイルと同じ）。文のブロックは伸びる textarea、写真は全幅の 1 枚。
  - 貼る: パレットの「写真」→ 選ぶ → シート（読み込む／置く）→ 「置く」で**いまのカーソル位置**に写真の
    ブロックが入る（そこで文が 2 つに割れ、次の文に caret が移る）。上がるまでは仮の枠（F3）。
  - 消す: 写真の右上の ×、または直後の文の先頭で BackSpace（Notion と同じ）。前後の文が繋がる。
  - 保存: 本文（プレースホルダ入り）+ `mediaUrls` + `effects.inlineImages`（offset はプレースホルダの位置、
    `layout: 'block'`、`widthRatio: 1`）。PC の `textSpans` 等は触らず持ち越す。
  - 本文の中に居ない写真（PC の旧形式・添付だけ）は今までどおり本文の下に積む。
- 場所: 新 `features/shared/entries/utils/inline-photos.ts`（純関数: 切る／位置を数える／差す／抜く、+test）、
  新 `features/sp/entries/components/sp-body-editor.tsx`（+verify +test）、`sp-entry-editor.tsx`
  （`initialEffects`、保存に `effects`）、`app/(protected)/entries/[id]/page.tsx`、
  `docs/entry-photo-guide.md`「いまやっていないこと」。
- 完了条件: 本文の途中で写真を置くとそこに入り、上下の文が続けて書ける。開き直しても同じ位置。PC で
  開くと同じ位置に写真がある（block・全幅）。

## H. 3 回目の指摘（同日 07:58、エントリー画面）

原文の要旨: (1) セミモーダルの中でスクロールし切ってさらに引いたら板を小さく（Google マップ: 半分で中身を
払うと板が上がり、全画面に着いた瞬間に同じ指で中身がスクロールし始める。戻りは逆。縦横は置いた直後に確定）。
(2) 全画面にすると下端の列がブラウザのバーの下に潜る。列は必ず触れる位置に。(3) 言葉・抜粋の理由は押さなく
ても最初から出す。(4)「発酵の結果」は開いていれば消す・消えていれば出す、だけの単純なボタンに。(5) 写真の下に
カーソルを置くと写真が画面を占めてカーソルが見えない。どんな状況でもカーソルは見えるように。(6) 写真を押したら
PC のように回り込み・配置・大きさを変えたい。(7) 取り込みの二択は同じ色に。(8) 設定のシートも同じ磨き込みを。
セミモーダルは共通部品で同じ品質に。(9) 設定を変えた結果を本文で確かめられるように。

### H1. 指の受け渡し（板 ⇄ 中身）を 1 本の指で

- [x] 直し方: `components/ui/sheet-gesture.ts` に**共通の手**を置き、`BottomSheet` と `DockSheet` の両方が使う。
  板は `touch-action: none`、中身の `scrollTop` も指の残りぶんで書く（ブラウザに渡すと途中で取り返せない）。
  上へ: 板を上げ、いちばん高い段に着いたら残りで中身をスクロール。下へ: 中身を先頭へ戻し、着いたら残りで
  板を下げる。離したら中身に慣性（自前）、板は近い段へ（速く払えばその向きの次の段）。置いた直後に縦か横かを
  確定し、横なら板は動かない。
- 完了条件: 半分の段で中身を上に払うと板が上がり、同じ指で中身が流れる。全画面で中身を下へ払うと先頭で板が下がる。

### H2. 下端の列が潜る

- [x] 原因: 全画面の段を**殻の高さ**の比で決めていた。殻 = 上段 + 本文 + 板 + 列なので、板 0.88 + 上段 + 列 が
  殻を超え、列が殻の外（ブラウザのバーの下）へ押し出された。
- 直し方: 段の高さは**使える高さ**（殻から上段・列など本文と席以外の兄弟を引いた分）から決める。全画面 = 使える
  高さそのもの。列は必ず殻の中に残る。

### H3. 理由は最初から

- [x] 言葉は「語 + 説明」の並び、抜粋は「本文 + 理由 + 日付」。押して出す段を無くす。

### H4. 「発酵の結果」は出す／消すだけ

- [x] 開いていれば消す。消えていれば半分で出す（フォーカスは外す）。段の切り替えはつまみと指に任せる。

### H5. カーソルはどんな状況でも見える

- [x] 原因: 写真の下の文にフォーカスすると、ブラウザの「入力欄を見せるスクロール」が写真ごと上へ持ち上げ、
  キーボードの上に写真だけが残ってカーソルは下に隠れた。
- 直し方: 本文の部品が**自分でカーソルを見せる**。鏡（同じ書体・幅の隠し要素）でカーソルの行の位置を測り、殻の
