# docs の方針 — ストックとフロー

`docs/` の文書は 2 種類しかない。どちらかを決めてから置く。

| | ストック | フロー |
| --- | --- | --- |
| 何か | 構造と規約。いつ読んでも真 | ある時点の判断・計画・作業指示・実装メモ |
| 日付・状態 | 持たない | 見出し直下に必ず持つ |
| 更新 | 上書き（履歴は git） | 追記。役目を終えたら `docs/archive/` へ移す（消さない） |
| 読む人 | 全員・毎回 | その作業をする人だけ |
| 置き場 | `docs/` 直下 | `docs/work/`（作業指示）・`docs/plans/`（計画）・`docs/<feature>/`（設計一式） |

**基本のアーキテクチャと規約を示すもの以外はすべてフロー。** ドメイン別の実装ガイドや画面設計も、
その時点の判断であってフローに入る。どれがどちらかは `docs/README.md` の索引が正。

## フロー文書の約束

1. 見出し直下に次を置く。
   ```
   状態: 進行中 | 完了 | 失効　　作成: YYYY-MM-DD　　最終更新: YYYY-MM-DD　　関連: PR / Issue
   ```
2. **完了・失効したら `docs/archive/` へ移す。** 索引からも外す。腐るのは「終わったのに残っている」文書。
3. フローで決めたことのうち、**今後も守る規約になったものはストックへ移す**（コピーしない。
   フロー側には「→ `docs/xxx.md` へ移した」とだけ残す）。
4. 追記型の実装メモ（`oryzae-study/60-implementation-notes.md` の類）は、**決着だけをストックへ**上げ、
   本体は区切りのよいところで archive へ。読み返す前提で書かない。

## 作業指示（`docs/work/`）の書き方

指摘が多い作業を、**新しいセッションがそのファイルだけ読めば始められる**ように切り出す。
コンテキストの上限は作業指示の側で制御する。

- 1 作業系 1 ファイル。`YYYY-MM-DD-<slug>.md`。
- 先頭に「前提として読むストック」を列挙する（それ以外は読まなくてよい、という宣言）。
- 項目ごとに **症状 / 原因 / 直し方 / 場所 / 確認 / 完了条件** を書く。原因が未確定なら「仮説」と書く。
- 進捗は項目のチェックボックスで持つ。終わった項目は消さず、PR 番号を添える。
- 全部終わったら「状態: 完了」にして archive へ。

## 索引

`docs/README.md` にストック / フロー / archive を分けて列挙する。追加・移動したら同じ PR で更新する。
