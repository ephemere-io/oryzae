# LLM 利用記録の設計（llm_usage_events）

Oryzae が Claude を呼ぶたびに「誰が・どの機能で・何を・どれだけ使ったか」を 1 回 1 行で残す。
金額の正は Anthropic、結果の正は各機能の表、**利用量の正はこの表**、と役割を分ける。

2026-09-26 起案。背景は日次コストレポートの「誰が使ったか」を全機能で出す要望と、
その過程で見えた「利用量の置き場が機能ごとにばらばら」という問題。

---

## 1. 現状（本番 DB とコードで確認した事実）

### LLM を呼ぶ機能は 3 つ

| 機能 | 結果の保存先 | 「誰が・トークン・成否」の記録 |
|---|---|---|
| 発酵 | `fermentation_results` ほか 5 表 | `fermentation_results` の列（`input_tokens` / `output_tokens` / `status` / `error_message` / `generation_id`） |
| ボード OCR | 保存を選んだときだけ `board_snippets.text` | **無い** |
| 写真の文字起こし | 本文に入れたときだけ `entries.content` | **無い** |

### 発酵の記録の実態（2026-09-26 時点）

| status | 行数 | トークンあり | generation_id あり |
|---|---|---|---|
| completed | 260 | 122 | 75 |
| failed | 36 | 0 | 0 |
| processing | 1 | 0 | 0 |

- 138 行の completed にトークンが無い（AI Gateway 時代は `generation_id` だけ、モデル retire 期間は何も無い）
- `generation_id` は AI Gateway の問い合わせ用だったが、Gateway もキーも撤去済みで、もう引けない
- **失敗した発酵はトークンも理由の分類も残っていない**（`error_message` の文字列だけ）
- **再試行は同じ行を使い回すので、前の試行のトークンは上書きされて消える**

### 金額

実額は Anthropic の cost_report（Workspace＝機能ごと）。DB には持たない。

---

## 2. 何が問題か

1. **利用量の置き場が機能ごとにばらばら。** 発酵は結果の表の列、OCR はどこにも無い。
   LLM の機能を足すたびに「どこに記録するか」を決め直すことになる
2. **結果の表に運用の情報が混ざっている。** `fermentation_results` は「発酵の結果」の表なのに、
   トークン・Gateway の ID・API エラー文が同居している
3. **1 回の呼び出しが 1 行になっていない。** 再試行が上書きされ、失敗は数えられない
4. **Anthropic の記録と突き合わせられない。** Console のログには request id が出るが、
   Oryzae 側にそれが無いので「このリクエストは誰のどの操作か」を辿れない
   （2026-09-21〜24 の課金急増の調査で、ここが無くて数日かかった）
5. **開発環境の利用が本番の数字に混ざる。** ローカルも本番の Supabase を向いているので、
   手元で OCR を試すと本番のユーザー別の数字に入る

## 3. 設計

### 役割の分担

```
                 ┌────────────────────────────────┐
  金額の正       │ Anthropic cost_report           │  Workspace = 機能ごとの実額
                 └────────────────────────────────┘
                 ┌────────────────────────────────┐
  利用量の正     │ llm_usage_events                │  1 呼び出し = 1 行（全機能）
                 └───────┬────────────────────────┘
                         │ fermentation_result_id（発酵のときだけ）
                 ┌───────▼────────────────────────┐
  結果の正       │ fermentation_results ほか       │  その機能が作ったものだけ
                 └────────────────────────────────┘
```

### 表: `llm_usage_events`

| 列 | 型 | 中身 | なぜ |
|---|---|---|---|
| `id` | uuid | | |
| `created_at` | timestamptz | 呼び出しが終わった時刻 | レポートの窓で引く |
| `user_id` | uuid null | 誰が | 退会したら null にする（下記） |
| `feature` | text | `fermentation` / `ocr_board` / `ocr_entry` | 機能。API キーの分け方と同じ |
| `environment` | text | `production` / `preview` / `development` | 開発・preview の利用を本番の数字から除く |
| `provider` | text | `anthropic` | 別の LLM を足したときに列を変えずに済む |
| `model` | text null | **実際に応答したモデル**（要求したものではない） | モデルの切替・フォールバックが起きても事実が残る |
| `outcome` | text | `succeeded` / `failed` | 失敗も 1 回として数える |
| `error_type` | text null | `spend_limit` / `rate_limit` / `overloaded` / `timeout` / `invalid_request` / `other` | 失敗の理由を分類で持つ。**エラー文は持たない**（本文が紛れ込む余地を作らない） |
| `input_tokens` | integer null | キャッシュを使わなかった入力 | |
| `cache_creation_input_tokens` | integer null | キャッシュ書込 | 単価が違う（1.25x / 2x）。キャッシュを入れたら推定がずれる理由がここに出る |
| `cache_read_input_tokens` | integer null | キャッシュ読込 | 単価が違う（0.1x） |
| `output_tokens` | integer null | 出力 | |
| `duration_ms` | integer null | 呼び出しにかかった時間 | OCR の待ち時間、タイムアウトの切り分け |
| `provider_request_id` | text null | Anthropic の request id | **Console のログと 1 対 1 で突き合わせられる** |
| `fermentation_result_id` | uuid null | どの発酵の試行か | 発酵の再試行が 1 回ずつ別の行になる |

**持たないもの**

- 日記の本文・読み取った文字・画像・プロンプト・エラー文
- 金額（実額は Anthropic、ユーザー別の推定はトークンから読むときに計算する）

### 金額を保存しない理由

保存すると、単価表の誤りや改定がそのまま過去の数字に焼き付く。実額は Anthropic が正で、
推定は「トークン × その時点の単価」で読むたびに出せる。単価の改定は、単価表に適用開始日を
持たせて扱う（必要になった時点で）。

### 権限（RLS）

| 誰が | 何を | どうやって |
|---|---|---|
| ユーザー本人 | 自分の行を書く | OCR はユーザーの JWT で書く。`auth.uid() = user_id` の insert ポリシー |
| サーバー（service role） | 書く・読む | 発酵（cron・手動）とレポート |
| ユーザー本人 | 自分の行を読む | **今は許可しない。** 「今月の使用量」をユーザーに見せる機能を作るときに足す |

service role の利用箇所は増やさない（発酵は既存の service role の経路で書く）。

### 退会したとき

`user_id` は `on delete set null`。**行は残し、誰のものかだけ消す。**

- 行に日記の中身は無い。残るのは「いつ・どの機能を・何トークン」だけ
- 過去の月の利用量と実額の突き合わせが、退会で崩れない
- 個人との紐付けは消えるので、退会の約束（あなたのデータは消える）は守れる

### 保持期間

当面は消さない。現在の量（発酵が月 100 件前後、OCR は月数十〜数百回と見込み）なら
10 年分でも数万行で、容量は問題にならない。退会で匿名化されるので、保持の理由で個人に
紐づく記録が残り続けることもない。量が増えたら「13 か月より古い行は月次集計に畳む」を足す。

### 索引

- `(created_at)` — 日次レポート・月次集計
- `(user_id, created_at)` — ユーザー別（管理画面、将来の上限）

## 4. 書き込み方

1 か所に寄せる。各機能の usecase が LLM を呼んだあと、成功でも失敗でも 1 行書く。

```
usecase
  ├ 時間を測りながら gateway を呼ぶ
  │    成功 → gateway が「実モデル・4 種のトークン・request id」を返す
  │    失敗 → 例外から「エラーの分類・request id」を取り出す
  └ recordLlmUsage(recorder, event)   ← 失敗しても本来の処理は止めない・await する
```

- **記録の失敗で本来の処理を失敗させない。** 記録はレポートのためのもの
- **await する。** fire-and-forget だと Vercel が応答後に関数を止めて書き込みが切れる
- `feature` の一覧はコードの 1 か所（API キーの対応表 `anthropic-provider.ts`）と同じものを使う。
  機能を足すときは「キーの対応表に 1 行 + migration の check 制約に 1 語」で済む

## 5. 将来こうなったら

| 起きること | この設計でどうなるか |
|---|---|
| LLM を使う機能を足す | `feature` に値を 1 つ足す。表は増えない |
| ユーザーごとに月の利用上限を設ける | `(user_id, created_at)` で今月分を数えるだけ |
| 有料プラン・従量課金 | 利用量の正がここにあるので、請求の元データになる |
| ユーザーに「今月の使用量」を見せる | 本人の select ポリシーを足す |
| プロンプトキャッシュを導入する | キャッシュのトークンが列として残る。推定と実額のずれの理由が数字で分かる |
| モデルを替える・フォールバックさせる | `model` が実際に応答したモデルなので、切替の前後が行で分かる |
| 別の LLM プロバイダを足す | `provider` に値を足す |
| 課金が急に増えた | `provider_request_id` で Console のログから Oryzae の誰の操作かを辿れる。行が無ければ Oryzae の外 |

## 6. 移行

2 段階。途中の状態（OCR は新しい表・発酵は古い列）を main に残さない。

### 段階 1（1 つの PR）

1. `llm_usage_events` を作る（migration）
2. 既存の発酵のうちトークンがある 122 行を移す（`model` は当時の記録が無いので null。推測で埋めない）
3. 発酵・ボード OCR・写真の文字起こしがすべてここに書く
4. 日次レポートと管理画面（コスト・ユーザー別・発酵の詳細）はすべてここから読む
5. 発酵は `fermentation_results` のトークン列と `generation_id` に書くのをやめる

### 段階 2（本番で数日動くのを確かめてから）

`fermentation_results` から `input_tokens` / `output_tokens` / `generation_id` と、
`generation_id` の索引を消す。migration の適用とデプロイの間に古いコードが古い列へ
書くことがあるので、段階 1 と同時には消さない。

## 7. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| OCR 専用の表（`ocr_usage_events`）を足す | 利用量の置き場が機能ごとに増え続ける。発酵だけ別の場所、の状態も残る |
| 発酵の列を残したまま、新しい表にも書く | 同じトークン数を 2 か所に持ち、ずれたときにどちらが正か分からなくなる |
| 結果の表に対象を指す汎用の列（`subject_type` + `subject_id`）を持つ | 外部キーで守れない。対象を持つ機能が発酵だけの今は、専用の列 1 本で足りる。増えたら列を足す |
| 金額を行に保存する | 単価の誤り・改定が過去に焼き付く。実額は Anthropic が正 |
| エラー文を保存する | 本文が紛れ込む余地を作る。分類で足りる |
| PostHog など外部の分析基盤に送る | 名前（メール）の解決と、実額との突き合わせが DB の外に出る。記録と処理が同じリクエストで確実に揃う DB に置く |
